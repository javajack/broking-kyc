> **Why this page is structured this way:** A broker building its own front end has to write between four and six independent decoders, and the reason is not that the venues chose differently once — it is that each venue's *families* of feeds chose differently too. One exchange ships a compressed proprietary broadcast, an uncompressed little-endian event stream and a big-endian commercial batch format, all simultaneously, all describing the same market. So the page is organised by encoding family rather than by venue, because the family is the unit of work: each one is a separate decoder, a separate sequence domain, a separate set of traps. The unresolved questions are collected at the end of each family rather than hidden, because on this subject what the documents do not say is as operationally important as what they do.

## TL;DR

- **There are at least four unrelated encoding families to implement**, not three: a compressed proprietary broadcast, an uncompressed little-endian order-event stream, a big-endian compressed commercial batch format, and a FAST-encoded multicast model shared in shape — but not in template numbering — by two venues. A fifth, the order-by-order binary, differs again.
- **One exchange uses two different byte orders in two of its own products.** The member order-event feed is little-endian; the commercial level feeds are big-endian. Reusing one parser for the other is a defect that produces plausible-looking nonsense.
- **A broadcast sequence number that looks global is explicitly not unique.** It is generated per host process, across eleven sequence sets on the normal broadcast and six on the fast broadcast. A single "previous plus one" gap test on it is unjustified and will fire constantly.
- **Eight bytes must be skipped before the message header.** The message header begins at the ninth byte of the decompressed broadcast data, and both compressed and uncompressed packets must be handled by the same code path.
- **A declared array size is not a maximum message size.** One venue's envelope declares a 512-byte data array while the same venue documents individual messages of 546 and 558 bytes. The real fragmentation rule is not published and must be obtained.
- **FAST template identifiers are per venue and per release, and one venue warns that its packet-header identifiers can change.** Two venues share the same message *names* and the same shape, and differ on the numbers. Hard-coding either venue's table against the other is wrong.
- **The order-by-order feed at one venue has no unambiguously documented order key.** The reserve-field mapping gives priority semantics while the individual message layouts mark those same fields unused. This has to be settled with the exchange before a book builder is written.

## Conceptual overview

Decoding market data is mechanically simple and conceptually treacherous, and the treachery is concentrated in three places. The first is the **envelope**: before any message can be read, a receiver has to know how many messages are in this datagram, whether the payload is compressed, what to skip, and where the message boundary is. Every venue answers these four questions differently, and two of the venues answer them differently across their own products. The second is the **sequence domain**: a sequence number is only useful if you know what it counts and what resets it, and the published answers range from "per stream per day, restarting at one" through "scoped by sender and by multicast address and port" to "explicitly not unique, generated by individual host processes". The third is **identity**: which field identifies an instrument, and — on an order-level feed — which field identifies an order. The first is always answered; the second is not.

The practical consequence is that a market data adapter is not one component with venue plug-ins. It is a set of decoders that happen to produce a common internal representation, and the only thing they share is that representation. Attempts to unify them earlier than that — a common packet-header abstraction, a shared sequence-gap detector, one endianness setting — reliably produce code that is correct for the venue it was written for and subtly wrong for the others. The honest architecture writes the decoders separately, tests each against captures from its own venue, and unifies only at the normalisation boundary described in [normalisation and internal distribution](/broking-kyc/finix-broking-setup/marketdata/05-normalisation-and-internal-distribution/).

The second structural point concerns what the documents are for. An exchange protocol manual is a contract for the release it describes, and these manuals are revised frequently — several times a year on the active segments. They also contain, demonstrably, internal inconsistencies: a message called by two different identifiers in two sections of one document; fields described as carrying priority information in one table and marked unused in another; a filename that names an older version than the document inside it. None of this makes the documents unusable; it makes **a test capture from the exchange's own environment a required part of the build**, not an optional validation step. Where this page records a conflict, the resolution is always the same: ask the exchange, and confirm in the test environment.

Finally, a boundary worth stating plainly. This page names envelopes, header fields, message families, template identifiers, compression algorithms, byte orders and sequence semantics, because these are the facts that determine the architecture and the ones an engineer must know in order to scope the work and ask the right questions. It does not reproduce byte-offset tables, field-presence rules or the encoding template packages. Those are supplied by the venue for the release a firm is provisioned on, and building from any third-party rendering of them — including this one — is how field-level defects enter a stack.

## 1. The families, named

| Family | Venue and product | Encoding | Byte order | Compression |
|---|---|---|---|---|
| **Proprietary broadcast** | <abbr title="National Stock Exchange of India">NSE</abbr> member broadcast on the trading connection | Fixed-layout structures with transaction codes | Per the segment manual | **Compressed, conditionally** — a length field of zero means uncompressed |
| **Order-event stream** | NSE member tick-by-tick multicast | Packed fixed structures with a stream header | **Little-endian** | None documented |
| **Commercial batch** | NSE commercial level and index feeds | Batch header, information header per message, trailer with checksum | **Big-endian** | LZO |
| **FAST multicast** | <abbr title="BSE Limited (formerly Bombay Stock Exchange)">BSE</abbr> and <abbr title="Multi Commodity Exchange of India">MCX</abbr> netted and enhanced market data interfaces | FAST, with a per-datagram reset | Network byte order | FAST's own field encoding |
| **Order-by-order binary** | BSE and MCX enhanced order book interfaces | Proprietary binary with template identifiers | Little-endian at MCX | **Uncompressed** at MCX |
| **Replacement-snapshot binary** | BSE Direct NFCAST | Message type in the first four bytes | **Big-endian** conversion instructed | Some message types require decompression |

<Aside type="danger" title="Two byte orders at one exchange">
NSE's member tick-by-tick specification describes **packed structures in little-endian format**. NSE's commercial level feed specification describes a **big-endian** batch format with a completely different envelope — a compression-and-count batch header, a per-message information header carrying a code, a length and a sequence number, and a trailer with a checksum and an end-of-transmission marker.

These are two products from one exchange describing the same market, and **neither parser can read the other's packets**. The failure mode is not an exception; it is plausible-looking numbers in the wrong fields, which is far worse. Keep the two decoders in separate modules with separate test captures, and never introduce an endianness configuration flag that one code path reads — a flag is an invitation to set it wrongly.
</Aside>

## 2. The NSE member broadcast envelope

| Layer | What the published specification establishes |
|---|---|
| **Outer envelope** | A broadcast packet structure carrying a two-byte network identifier, a count of packets, and the packed packet data. Published network identifiers: **equity 4, equity derivatives 2, currency derivatives 6** |
| **Packet count** | The envelope **can contain several packets**, and the count field must be used. A separately stated maximum count per datagram is not published |
| **Compression wrapper** | A length field followed by the broadcast data. **Zero means uncompressed**; a non-zero value is the compressed length. Both cases must be handled by the same receiver |
| **Decompressor** | The published implementation instructions name an **LZO** decompression entry point and an LZO version. This is not a generic deflate path |
| **The eight bytes** | **Eight system-header bytes precede the message header and must be ignored.** The message header begins at the **ninth byte** of the decompressed broadcast data |
| **Message header** | A **forty-byte** header whose fields include a log time, a two-character alphabetic field, the **transaction code**, an error code, a **broadcast sequence number**, a timestamp, a filler that **carries the machine number**, and a **message length that includes the header itself** |
| **Transport security** | The **interactive** connection is protected — a TLS session to the gateway router and an authenticated encrypted channel for the allocated gateway. **These clauses do not establish any encryption on the UDP multicast broadcast**, and the published material does not assert it |
| **The packet-size question** | **Unresolved.** See section 7 |

<Aside type="danger" title="The broadcast sequence number is explicitly not unique">
NSE's own specification states that the broadcast sequence number is **not unique**: there are **eleven sequence sets on the normal broadcast and six on the fast broadcast**, generated by individual host processes, with the machine number carried in a separate filler field.

The consequence is that the obvious gap detector — compare this packet's sequence to the last one plus one — is **unjustified** and in practice fires continuously. A complete public mapping from host process to sequence domain, and a normative gap-repair algorithm, are **not published**.

What to do: do not build a gap detector on this field without the exchange's own sequence and recovery specification. Treat the broadcast as a best-effort state feed whose correctness is established by other means — the end-of-day files for the reproducible record, and the order-event feed where exactness matters — and reserve sequence-based gap detection for the feeds that document a usable sequence domain. This is covered in [gap recovery and arbitration](/broking-kyc/finix-broking-setup/marketdata/04-gap-recovery-and-arbitration/).
</Aside>

### 2.1 The broadcast message families

Transaction codes are **segment-specific**, and the cash and derivatives tables differ for the same logical message. The families a receiver must handle:

| Family | Note on the cash and derivatives difference |
|---|---|
| Market by price | The derivatives feed's **enhanced** variant supersedes the legacy code on the migrated feed. Two different codes for the same logical message, one per segment generation |
| Combined market-by-order and market-by-price | Documented with five buy and five sell entries. Its **current production emission is not established**, so do not design a dependency on the order-level component of this broadcast message — the order-level product is the tick-by-tick feed |
| Market watch | Shares a code between segments in the current generation, where the migration **replaced** an enhanced code with the legacy number — a replacement in the opposite direction from the other messages |
| Ticker and trade summary | **Different codes in cash and derivatives, and the derivatives revision history strikes out the legacy one.** Substituting one segment's code for the other is a specific, documented error |
| Index, and volatility index | Published in the cash table. **Do not infer identical index messages on every derivatives stream** |
| Open interest | The derivatives feed carries an **underlying-security** open-interest message with a wide current-open-interest field and multiple records per message. This is **distinct from contract open interest** |
| Security and contract master change | Different codes per segment. **Must be applied intraday**, not logged — this is the path by which freeze quantities and other master attributes change during the day |
| Security status, including a pre-open variant | Per segment |
| Market status, including the session transitions | Use **the selected segment's own table**; a cash code list is not a cross-segment contract |
| Spread depth | Derivatives only, with an enhanced code replacing the legacy one on the migrated feed |
| Closing auction session | Status transitions and a reference-price broadcast are published in the cash table. **Do not apply cash auction codes to derivatives** without that segment's own specification |

## 3. The NSE member tick-by-tick stream

| Element | What the specification establishes |
|---|---|
| **Stream header** | An **eight-byte** header carrying a message length, a **stream identifier** and a **sequence number**. The derivatives variant widens the sequence field to unsigned |
| Structure packing | **Packed structures, little-endian** |
| **Sequence domain** | **Per stream, starting at one each day and incrementing.** A disaster-recovery switchover **can reset it to one** |
| **Heartbeat** | Carries header sequence **zero** and the **last sequence number** sent. This makes "nothing has happened" distinguishable from "I have missed everything" |
| Order events | Order **addition, modification and cancellation**, with distinct spread equivalents. Order identifiers make exact book reconstruction possible |
| Trade events | **Trade**, **spread trade** and **trade cancellation**. The trade structure carries a timestamp, the buy and sell order identifiers, the token, the price and the quantity |
| **Timestamp epoch** | **Nanoseconds since 1 January 1980** — not the Unix epoch. The other venue's order-book feed uses a different epoch, and a back office that ingests both will hold two |
| Session behaviour | Pre-open order collection is withheld under the specified pre-open handling, while matching-phase trades are disseminated. **The closing auction session behaves differently from pre-open** — auction orders *are* disseminated during collection, market orders carry price zero, matching-phase trades carry both order identifiers, and remaining-order cancellations are disseminated at session end |
| What "full order book" does not mean | **Not** visibility into every hidden or non-displayed order state |

<Aside type="tip" title="The heartbeat carrying the last sequence number is the most useful field on this feed">
A sequenced stream has a silent failure mode: if nothing arrives, the receiver cannot tell whether the market is quiet or the feed is gone. This feed resolves it — the heartbeat carries sequence zero in its own header and reports the **last sequence number disseminated**, so a receiver always knows both that the feed is alive and exactly where it should be.

Build the staleness and gap detection around that field rather than around a wall-clock timer, and the two commonest market data monitoring defects — alerting on quiet markets, and failing to notice a dead stream — both disappear.
</Aside>

## 4. The NSE commercial level and index feeds

| Element | What the specification establishes |
|---|---|
| **Envelope** | A **batch header** carrying a compression indicator, a data size and a packet count; a **per-message information header** carrying a code, a length and a sequence number; and a **trailer** with a checksum and an end-of-transmission marker |
| Compression | **LZO** |
| **Byte order** | **Big-endian** |
| Depth | **Level 1** best bid and offer; **Level 2** five price levels; **Level 3** twenty price levels. These are **price-depth products, not an order-identified event book** |
| Published cadence | The cash specification's own answer describes an **initial packet within six to nine seconds, then updates or repeated packets every five seconds**, with illiquid-security packets repeated twice under the current configuration. A universal cadence across all segments is not published |
| Index messages | A **live index** message, an **end-of-day** message, and a **heartbeat every two seconds** when there is no data, carrying sequence zero. The heartbeat interval is **not** evidence of a two-second index update rate |
| Auction messages | The cash feed documents an auction message sequence — reference price, auction updates, start, market-order restriction and end — with a published timing table |
| **A documented internal conflict** | The cash manual's **narrative** names the normal-market-close-for-auction message with one identifier and its **own timing table** names it with another. The authoritative identifier requires an exchange erratum and a captured test feed. **Do not silently pick one** |
| Sequence and recovery | Application sequence numbers exist in the format. **A universal public replay or snapshot service for all of these products is not established**, and the member tick-by-tick recovery service must not be silently applied to them |

## 5. The FAST multicast model at BSE and MCX

Both venues publish the same datagram shape, which is worth internalising because it is unlike the others on this page:

| Element | Published model |
|---|---|
| **Datagram** | **Packet header → FAST reset → one or more messages** |
| **Message** | A presence map, then a **template identifier**, then the data |
| Byte order | **Network byte order** |
| **Decoding independence** | **Each datagram decodes independently** — which is what the per-datagram reset is for, and what makes packet loss survivable at the decode layer even when it is not survivable at the book layer |

### 5.1 Packet headers differ between the netted and enhanced interfaces

| Interface | Header fields published |
|---|---|
| **Enhanced** market data interface | A **partition identifier**, a sender identifier, a **packet sequence number**, a sending time, and a **performance indicator** that is present on incrementals only. At one venue the performance indicator describes the timing from trading-interface input to the market data socket; at the other venue the same field is **unused** |
| **Netted** market data interface | A sender identifier, a packet sequence number and a sending time — **no partition identifier and no performance indicator** |
| Packet sequence scope | **Scoped by sender and by multicast address and port.** Not global, and not per product |

### 5.2 Template identifiers are per venue and per release

The two venues publish the **same message names** and **different numbers**. A representative set, read from one BSE release and one MCX release:

| Message | BSE enhanced | BSE netted | MCX enhanced | MCX netted |
|---|---:|---:|---:|---:|
| Functional beacon | 109 | — | 109 | — |
| Packet header | 111 | 116 | 60 | 65 |
| FAST reset | 120 | 120 | 120 | 120 |
| Depth snapshot | 93 | 101 | 93 | 101 |
| Depth incremental | 94 | 102 | 94 | 102 |
| Product state change | 97 | 108 | 97 | 108 |
| Instrument state change | 98 | 103 | 98 | 103 |
| Mass instrument state change | 99 | 104 | 99 | 104 |
| Complex instrument update | 124 | 105 | Not listed | Not listed |
| Index statistics | Not established | Not established | 50 | 51 |

Three cautions on this table. The **depth and state identifiers happen to coincide** between the two venues in this pair of releases, which makes it tempting to treat them as a standard — they are not, and the packet-header numbers in the same row prove it. The BSE numbers above are from a **historical release**, and the BSE manual itself **warns that packet-header identifiers can change**. And a message **not listed** at one venue is a listing difference in these releases, not proof of universal absence.

### 5.3 Snapshot and incremental semantics

| Element | Published behaviour |
|---|---|
| Snapshot nature | **Time-driven, per instrument.** The incremental reflects book changes |
| Depth configured by the exchange | A market-depth field carries the number of levels, and it is an **exchange configuration**, not a client choice |
| **The linkage field** | On the **enhanced** interface, depth snapshots **omit the message sequence number** and instead carry a **last-message-sequence-number-processed** field, which is what links a snapshot to the incremental stream |
| The netted interface differs | Its snapshots **use the message sequence number** and a **refresh indicator**, and **not** the linkage field. A refresh indicator set to yes **requires** applying the refresh |
| Update actions | The depth incrementals publish an update-action enumeration covering **new, change, delete, delete-through, delete-from and overlay**. Delete-through and delete-from are range operations and are the two that a naive implementation gets wrong |
| Circuit limits | One venue's version 1.6 **adds upper and lower circuit limit entry types to the depth incrementals**, with a stated parser deadline. Band information therefore arrives on the depth path and must be **applied**, not logged |
| **What these interfaces are not** | They describe **aggregated price levels, not individual orders.** Their depth-entry identifiers **must not** be used as exchange order identifiers |

## 6. The order-by-order binary feeds

### 6.1 MCX

| Element | Published detail |
|---|---|
| **Envelope** | A **packet header** followed by messages **for one product** |
| Message header fields | A **body length**, a **template identifier** and a **message sequence number** |
| Packet body fields | An **application sequence number**, a market segment identifier, a **partition identifier**, a **completion indicator**, an **application sequence reset indicator**, padding and a transaction time. The **packet header's own message sequence number is unused** |
| Encoding | **Uncompressed, little-endian** |
| **MTU** | **1,372 bytes** |
| Template families | Order **add, modify, delete and mass delete**; **full and partial order execution**, and order-modify-same-priority; **trade report** and **execution summary**; product, instrument and mass instrument state change; **top of book**; product summary, instrument summary and **snapshot order**; instrument information and index information. Heartbeat and packet header have their own identifiers |
| Sequence roles | The **application sequence number sequences channel packets**; the **message sequence number sequences product updates**. Two different domains in one feed, and both are needed |
| **The order-key problem** | **Unresolved in the published manual.** Its reserve-field mapping associates two reserve fields with **previous and new priority**, while the **individual message layouts mark those same fields unused**. An unambiguous supported order key is therefore **not established** |

<Aside type="danger" title="Do not invent the order key">
A book builder for an order-by-order feed needs one thing above all others: a stable identifier for an order across its add, modify, execute and delete events. For this venue, the manual's own two descriptions of the candidate fields contradict each other.

The correct action is to obtain corrected layouts and **sample add, modify, delete and execution packets** from the exchange before writing the builder. The two wrong actions, both of which happen: inventing an order identifier field by analogy with another venue's protocol, or assuming the generic timestamp-based key used by the upstream platform family. Either produces a book that is right in testing and wrong under modification-heavy load, which is the hardest class of defect to find afterwards.
</Aside>

### 6.2 BSE

The BSE order-book manual and its current binary layout were **not obtainable**. Its header, template identifiers, order key, timestamps, quantity widths and sequence and reset fields are **unverified**. The MCX identifiers above are **not** BSE verification, and must not be used as such. Obtain the current BSE order-book manual and its layout package from the exchange. Note also that this feed is **colocation-only** at BSE, so for many firms the question does not arise — see [the feed catalogue](/broking-kyc/finix-broking-setup/marketdata/01-feed-catalogue/#5-bse).

### 6.3 BSE's replacement-snapshot binary

| Element | Published detail |
|---|---|
| Message typing | The **first four bytes** identify the message type |
| Read guidance | The manual instructs a **2,000-byte read** and **big-endian** conversion. That guidance is not a claim about any individual message's length |
| Compression | Three market-picture message identifiers **require the documented decompression**; one of them carries an **eight-byte spread token** |
| **Sequence** | The manual states explicitly that **no product or stream sequence number exists** |
| Consequence | A gap is invisible, and is also self-healing for **state** — the next complete snapshot replaces the book. The **intermediate events and their chronology are gone permanently**, which makes this feed unusable as a surveillance or reconstruction input |

## 7. The questions the documents do not answer

Carry these as an explicit register with an owner, because each one is a decision someone will otherwise make by guessing.

| Question | Why it matters | What settles it |
|---|---|---|
| **Maximum datagram and decompressed size on the NSE broadcast** | The envelope declares a **512-byte** data array; the same venue documents a **546-byte** cash ticker message and a **558-byte** enhanced derivatives depth message. Compression may explain some cases, but there is no published fragmentation rule. **Do not turn the declared array into an assumed maximum** | The current broadcast transport specification or an exchange clarification covering both compressed and uncompressed cases, plus production and test captures |
| The interactive packet limit | The interactive chapter describes a **1,024-byte** maximum. Applying it to the multicast envelope **mixes two different packet definitions** | Treat them as unrelated |
| **NSE broadcast sequence mapping and gap repair** | Section 2 — the field is not unique and the process mapping is not published | The exchange's broadcast sequence and recovery specification, and the receiver application manual. Interactive recovery documentation does **not** settle multicast recovery |
| Maximum tick-by-tick datagram size | A universal payload or MTU figure is not published. The recovery snapshot's size limit is **not** a multicast datagram limit | The current network and interface specification |
| **Current FAST template packages** | Only historical identifiers at one venue were verifiable, and that venue warns the packet-header numbers can change | The venue's **XML template package** for the provisioned release. A logical field table is **not sufficient to build a decoder** |
| **The MCX order key** | Section 6.1 | Corrected layouts plus sample packets |
| **BSE order-book layout entirely** | Section 6.2 | The current manual and layout package |
| The auction close message identifier | One document names it two ways | An exchange erratum and a captured test feed |
| Index update cadence anywhere | Heartbeat intervals are not update rates, and no cadence or latency guarantee is published for the broadcast or the level feeds | The dissemination-frequency annexures for each product |
| Whether multicast is ever encrypted | The interactive path's security clauses do not extend to the broadcast, and no multicast protection is asserted | Explicit exchange confirmation, if a firm's own controls require it |

## 9. Exception paths

| Situation | Response |
|---|---|
| Decoded values are implausible but parsing succeeds | Suspect byte order and the wrong module before suspecting the feed. This is the signature of a cross-family parser reuse |
| Every field appears shifted by a constant | The skipped system bytes, or a header length assumption. Check against a fixture |
| Gap alerts fire continuously on the broadcast | Expected if the gap test is on the non-unique broadcast sequence. Remove the test rather than widening it |
| A message arrives larger than the declared array size | Do not truncate. Log, capture and raise with the exchange; this is the unresolved packet-size question |
| A sequence resets to one mid-session | Check for a documented reset — a disaster-recovery switchover resets one feed's stream sequences to one — before treating it as a gap |
| A template identifier is unknown | Store and alert, never discard. Then check whether the venue has changed its package |
| Order modify or delete events cannot be matched to an order | Stop and settle the order key with the exchange. Do not infer it |
| Range delete actions leave the ladder inconsistent with a later snapshot | The range operations are the likely defect. Test them explicitly against a fixture |
| Circuit limits appear on the depth path and are ignored downstream | They are band information and must be applied. See [normalisation](/broking-kyc/finix-broking-setup/marketdata/05-normalisation-and-internal-distribution/#3-conflation-stated-as-a-policy) |
| Two sections of one exchange document disagree | Record both, raise an erratum request, and block the dependent code path until answered |
| A manual's filename disagrees with its internal version | Pin the content and the circular number |
| A snapshot cannot be linked to the incremental stream | Check which interface you are on: the netted and enhanced interfaces use **different** linkage mechanisms |

## Practical notes

- **Get a test capture per encoding family before writing the decoder.** The documents are contracts for a release and contain known inconsistencies; a capture is the only thing that settles them.
- **Never share a parser across families, and never make endianness a setting.** Separate modules with separate fixtures cost a day and save a class of defect that is almost undiagnosable in production.
- **Build the gap detector per feed, from that feed's documented sequence domain.** Four feeds on this page have four different answers, and one has none at all.
- **Use the heartbeat's last-sequence field where it exists.** It is the one mechanism that distinguishes a quiet market from a dead feed without a timer.
- **Keep the unresolved-question register in the repository, not in someone's head.** Each item has an owner, an exchange contact and a blocked code path, and that is a tracked engineering artefact.
- **Pin template packages and protocol versions with their circular numbers.** A migration that replaces identifiers is a dated cutover, not a configuration change.
- **Implement the range delete actions deliberately and test them.** They are the part of the depth model that a reasonable implementation gets wrong.
- **Treat the replacement-snapshot feed as state-only, permanently.** No amount of engineering recovers a sequence from a feed that does not have one.
