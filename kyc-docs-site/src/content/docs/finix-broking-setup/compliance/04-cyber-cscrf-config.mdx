> **Why this page is structured this way:** Cyber security documentation is usually a framework restatement. This page is not; it assumes the framework is known and asks the implementation question: for each control domain, what is configured, what evidences it, and who owns it. The one domain treated at length is client-facing authentication, because it is where a broking firm differs from an ordinary business and where the regulatory requirement is most specific.

## TL;DR

- **Cyber security and cyber resilience became statutory in January 2026.** Regulation 18(5) of the [2026 regulations](/broking-kyc/finix-broking-setup/setup/02-sebi-registration-2026/) requires a robust framework, which moves it from a circular obligation to a condition of registration.
- **Two-factor authentication is mandatory for internet-based trading and wireless trading, and the two factors must not be the same.** This is specific, long-standing and frequently implemented loosely.
- **Nine control domains** cover the implementation: identity and access, privileged access, network segmentation, client-facing authentication, data protection, change management, logging and monitoring, vendor security, and resilience.
- **The order path is a segmentation boundary**, not just an application. It should not share a network with general corporate traffic.
- **Logging must survive the primary site** and be retained on the eight-year records floor; losing the diagnostic record with the system is a common and avoidable design defect.
- **Vendor security is in scope.** Six vendor integrations touch client personal data and the firm remains accountable.
- **Testing is the evidence.** Vulnerability management, drills and audits produce the records that demonstrate the framework operates.

## 1. Framework

- **[SEBI (Stock Brokers) Regulations, 2026](/broking-kyc/finix-broking-setup/setup/02-sebi-registration-2026/)** — **regulation 18(5)**, a statutory obligation to maintain a robust cyber security and cyber resilience framework. Also Chapter IV fraud prevention and detection, which assumes the systems can detect. `[not yet in index]`
- **Cybersecurity and Cyber Resilience Framework** for market intermediaries, with tiered obligations by size and criticality. See [CSCRF deep dive](/broking-kyc/deep-dives/compliance-audit/cscrf-deep-dive/).
- **Two-factor authentication for internet-based trading and securities trading through wireless technology** — a minimum of two factors in the authentication flow is mandatory and **the two factors must not be the same**; see [client protection frameworks](/broking-kyc/trading-risk/client-protection-frameworks/) for the circular chain, including the cyber-security annexure requirements such as a cryptographically secure biometric mechanism for mobile applications and account lock after failed attempts.
- **System audit framework** — see [system audit](/broking-kyc/deep-dives/compliance-audit/system-audit/).
- **Digital Personal Data Protection Act, 2023 and its rules** — the firm as data fiduciary; see [DPDP consent fields](/broking-kyc/reference/field-atlas/sections/aa-dpdp-consent/) and the [MeitY circulars index](/broking-kyc/reference/circulars/meity/).
- **Business continuity and disaster recovery** — see [BCP and DR drill](/broking-kyc/deep-dives/specialty/bcp-dr-drill/).

<Aside type="caution" title="What the statutory shift changes in practice">
Before January 2026 a cyber framework was required by circular; now it is required by regulation, as a condition of registration. Three consequences follow. The obligation cannot be relaxed by a circular, only by amendment. A breach is a breach of regulations rather than of an operational requirement. And an inspection will test the framework against the regulation's words — a robust framework — rather than against a checklist, which in practice means it will test whether the controls actually operate rather than whether they are documented.
</Aside>

## 2. The nine domains

### D1 — Identity and access

| Control | Configuration | Evidence |
|---|---|---|
| Central directory, one identity per person | Directory configuration | Directory |
| Role-based access from templates | Per-role entitlement maps across all nine systems | Role definitions |
| Least privilege | Entitlement review | Review records |
| **Joiner, mover, leaver** | **Same-day leaver checklist spanning every system** | Completed checklists |
| Mover handling | Remove before grant | Change records |
| Periodic recertification | By the role owner | Recertification records |
| **Certification coupling** | Entitlements for certified functions gated on a valid certificate | Certification register |
| Segregation of duties | The [incompatible pairs](/broking-kyc/finix-broking-setup/setup/07-people-certification-org/#5-segregation-of-duties--the-real-headcount-floor) | Role design |

### D2 — Privileged access

| Control | Configuration | Evidence |
|---|---|---|
| Separate privileged identities | Not daily-use accounts | Directory |
| **Time-bound elevation** | Just-in-time, with an expiry | Elevation records |
| Approval | Per elevation | Approval records |
| Session logging | Full | Logs |
| Review | Periodic, of all privileged access | Review records |
| **Vendor support access** | **Just-in-time, supervised, logged** — never standing | Access records |
| Break-glass | Sealed, tested, logged distinctly | Test records |

### D3 — Network segmentation

| Control | Configuration | Evidence |
|---|---|---|
| **Order path segmented** | Separate from corporate and general traffic | Architecture and firewall rules |
| Back office segmented | Separate zone | As above |
| Management network | Separate | As above |
| Exchange connectivity | Dedicated, with diverse paths | Link inventory |
| Egress control | Restricted and logged | Rules and logs |
| Firewall rule review | Periodic, with removal of unused rules | Review records |
| **Blast radius** | A compromise in one zone does not reach the order path | Architecture, tested |

### D4 — Client-facing authentication

The domain where a broking firm's requirements are most specific.

| Control | Requirement |
|---|---|
| **Two-factor authentication** | **Mandatory for internet-based trading and trading through wireless technology** |
| **Factor distinctness** | **The two factors must not be the same** |
| Mobile applications | A cryptographically secure biometric mechanism where applicable |
| Account lock | After a defined number of failed attempts |
| Session management | Timeout, concurrent-session control, re-authentication for sensitive actions |
| Device and session visibility | The client can see active sessions |
| **Sensitive actions re-authenticated** | Bank-account change, pay-out, DDPI changes |
| **Notification on change** | To the **previously registered** contact details as well as the new |
| Credential recovery | Hardened; this is the common attack path |
| Client education | Phishing, SIM swap, and the validated UPI handle |

See [client protection frameworks](/broking-kyc/trading-risk/client-protection-frameworks/) for the wider client-side stack, including the proposed device and SIM binding framework and SEBI Check.

| Control | Configuration | Evidence |
|---|---|---|

## 3. Incident classification and reporting

| Class | Examples | Internal | External |
|---|---|---|---|
| **Confirmed data breach** | Client personal or financial data exposed | S1; designated director; compliance | Per the applicable reporting obligation and timeline |
| Security incident without confirmed exposure | Intrusion attempt, malware contained | S2 | Per the framework |
| Account takeover | Client credentials compromised | S1 for the client | Per the obligation; client informed |
| Availability incident with a security cause | Denial of service | S1 or S2 | Per the obligation |
| Vendor incident affecting the firm | Vendor breach | S1 or S2 | The firm remains accountable |
| Insider incident | Misuse by a person with access | S1; outside the line | Per the obligation |

| Control | Detail |
|---|---|
| **Vendor notification window shorter than the firm's** | Contractual, in hours — see [vendor contracts](/broking-kyc/finix-broking-setup/setup/09-vendor-onboarding-contracts/#2-the-clauses-that-close-the-accountability-gap) |
| Classification decided early | It drives the reporting obligation |
| Evidence preservation | Before remediation, where feasible |
| Client communication | Prepared template, legally reviewed in advance |
| Post-incident | Root cause, dated actions, closure |

## 6. Exception paths

| Situation | Response |
|---|---|
| Confirmed data breach | S1; classify; preserve evidence; report per the obligation and timeline; inform affected clients |
| Account takeover reported by a client | Freeze; investigate; the change-then-withdraw review should have caught it |
| Vendor reports a breach | The firm remains accountable; assess exposure; report per the firm's own obligation |
| A leaver's access found active | Control failure; revoke; investigate the checklist; sample-test the rest |
| Standing vendor access found | Convert to just-in-time; review what was accessed |
| **A bypass of the risk release point found** | **Stop trading**; remediate; treat as a severity-one control failure |
| Logs lost with a site failure | Design defect; fix the replication; the diagnostic record for that incident is gone |
| Clock drift detected | Investigate; records written in the window are suspect |
| Production data found in a non-production environment | Severity one; remove; assess exposure; investigate the path |
| A drill fails | Dated remediation; an untested secondary site effectively does not exist |
| Two-factor authentication using the same factor twice | Non-compliant; fix immediately |

## Practical notes

- **Check that your two factors are actually different.** It is specific, long-standing, and the most commonly loose implementation in client-facing security.
- **Keep logging and identity off the primary site's fate.** Both are needed precisely when the primary site is gone.
- **Segment the order path.** It is the asset whose compromise is least recoverable.
- **Notify sensitive changes to the old contact details.** If the change is fraudulent, those are the details that reach the client.
- **Make vendor breach windows contractual and short.** The firm's clock starts when the vendor's does.
- **Test the bypass absence every release.** It is cheap and it protects the control everything else depends on.
- **Run the business continuity drill live.** A tabletop exercise proves the plan is readable, not that the site works.
