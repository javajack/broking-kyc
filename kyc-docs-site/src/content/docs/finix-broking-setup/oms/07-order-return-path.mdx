> **Why this page is structured this way:** The forward path has one outcome that matters — released or not. The return path has eight or nine, several of which are rare enough that they are discovered in production, and each of which has to propagate correctly into four places: the order state, the position, the risk engine's utilisation, and the client's view. So the page enumerates every message class, states what it means and what must happen, then treats propagation as a separate concern because propagation ordering is where the subtle defects live, then handles the hard cases — freezes, unsolicited messages, out-of-order arrival and end of session — that a naive implementation gets wrong.

## TL;DR

- **The return path has more states than the forward path, and most production defects live there.** Acknowledgement, rejection, partial fill, full fill, trigger, freeze, exchange cancellation and unsolicited messages are all distinct and all must be handled.
- **A rejection code must be mapped, never passed through.** An exchange reason code is correct and useless to a client. Map every code to an intelligible message and an action; alert on any code you have not seen before.
- **A partial fill is not a small full fill.** The remaining quantity is still live, still carries margin, still counts against limits, and still needs the client to understand that the order is working.
- **A freeze is neither live nor rejected.** A quantity or value freeze puts the order into a pending state awaiting exchange approval, and representing it as either live or rejected produces wrong client behaviour and wrong risk numbers.
- **Unsolicited messages exist and must be handled.** An exchange may act on an order without the broker asking — cancellation at end of session, cancellation on a corporate action or contract change, administrative action. Ignoring a message class because it is rare is how order state diverges.
- **Propagation order matters.** Position before risk utilisation before client view; getting this backwards shows the client a fill the risk engine has not yet accounted for, which is the window in which an over-limit order can be accepted.
- **Reconcile counts and values with the exchange during the session, not only at end of day.** Divergence found at 10:30 is an incident; the same divergence found at 17:30 is a settlement problem.

## Conceptual overview

Sending an order is a single act; learning what happened to it is an open-ended stream. That asymmetry is the source of most of the difficulty. A forward path can be reasoned about as a function — inputs in, decision out — while the return path is a long-running conversation in which the exchange may say something about an order minutes or hours after it was sent, and may say something the broker did not ask about. Systems designed around the forward path tend to treat return messages as confirmations of an expected outcome, which works until the exchange sends something unexpected, at which point the system has no place to put it.

The right mental model is that the exchange is authoritative about order state and the broker is maintaining a replica. Every return message is an update to the replica, the replica can drift, and drift is detected by reconciliation rather than by the absence of errors. This is why intraday reconciliation of order and trade counts against the exchange belongs in the operating rhythm and not only in the end-of-day process: the cost of divergence rises through the day, and a difference found in the morning can be investigated calmly while the same difference found after the close collides with the contract-note deadline.

The third idea concerns propagation. A fill is not one event; it is the same event that must land in the order state, the position, the risk engine's utilisation, the client's screen, and eventually the ledger. These are different systems with different latencies, and the order in which they learn matters. If the client's screen updates before the risk engine does, there is a window in which the client can act on a position the risk engine does not yet know about. The window is small and it is exactly the kind of small window that a fast client, or an algorithm, will find.

## 1. Message classes

| Class | Meaning | Order state effect | Must also do |
|---|---|---|---|
| **Acknowledgement** | Exchange accepted and assigned its order identifier | `SENT` → `ACKNOWLEDGED` | Store the exchange order identifier; it is the key for all later messages |
| **Rejection** | Exchange declined the order | → `REJECTED_EXCHANGE` | Map the code; release the blocked margin; inform the client with an actionable message |
| **Partial fill** | Part of the quantity traded | `ACKNOWLEDGED` → `PARTIALLY_FILLED` | Update position, utilisation, average price; remaining quantity stays live |
| **Full fill** | Entire quantity traded | → `FILLED`, terminal | Update position, utilisation, release residual blocks |
| **Trigger** | A stop-loss order's trigger price was reached or surpassed; the order is released into the Regular Lot book | `PENDING_TRIGGER_EXCHANGE` → `ACKNOWLEDGED` as a live order | Client notification; the order is now visible and behaving as its released type |
| **Freeze** | Quantity or value freeze; the order awaits exchange approval | → `FROZEN` | Represent as pending; keep margin blocked; follow the exchange approval process |
| **Freeze outcome** | Approved or rejected | `FROZEN` → `ACKNOWLEDGED` or `REJECTED_EXCHANGE` | Propagate accordingly |
| **Modification confirmation** | A modification was accepted | Attributes updated | Recompute margin; priority may have reset — see [modification rules](/broking-kyc/finix-broking-setup/oms/08-modify-cancel-rules/) |
| **Modification rejection** | Modification declined | Order unchanged | The original order is still live; say so clearly |
| **Cancellation confirmation** | Cancellation accepted | → `CANCELLED`, terminal | Release margin |
| **Cancellation rejection** | Cancellation declined, usually because the order already filled or is gone | Order unchanged or already terminal | **The most confusing case for clients**; resolve the true state before messaging |
| **Exchange cancellation** | Exchange cancelled the order — end of session, contract change, corporate action, administrative action | → `CANCELLED_BY_EXCHANGE` | Client notification; release margin; do not silently treat as a client cancellation |
| **Unsolicited message** | Anything the exchange sends that the broker did not request | Varies | Must be parsed and handled; an unhandled class is a divergence source |
| **Trade modification or cancellation** | A trade is modified or cancelled by the exchange | Position and obligation change | Rare, consequential, and must flow to the back office; see [trade import](/broking-kyc/finix-broking-setup/backoffice/02-trade-import-reconciliation/) |

<Aside type="caution" title="The cancellation-rejection race">
A client presses cancel; in the same instant the order fills. The exchange rejects the cancellation because there is nothing left to cancel, and sends a fill. Two messages arrive, possibly out of order, and the client sees either "cancellation failed" or "order filled" depending on which the interface renders last. The correct behaviour is to resolve to the true terminal state — filled — and to tell the client plainly that the order filled before the cancellation could take effect. Showing "cancellation failed" alone, with no explanation, generates a complaint in which the client believes the broker ignored their instruction.
</Aside>

## 2. Rejection code mapping

| Requirement | Detail |
|---|---|
| Complete mapping | Every exchange reason code mapped to a client message and an internal category |
| Unknown code handling | A code not in the map produces a generic client message **and an engineering alert**; unknown codes are how protocol changes announce themselves |
| Category | Price-related, quantity-related, instrument-related, client-related, member-related, session-related, risk-related |
| Actionability | The client message must say what to do differently, not what went wrong internally |
| Monitoring | Rejection rate by code, with alerting on rate changes and on new codes appearing |
| Attribution | A rejection caused by broker configuration is a defect, not a client error; separate the two in reporting |

| Exchange rejection family | Typical client message shape |
|---|---|
| Outside the price band | "The price is outside the exchange's permitted range for this instrument right now (currently A to B)." |
| Limit Price Protection | "The exchange rejected this price as too far from the current market. Try a price closer to the last traded price." |
| Lot or tick multiple | "Quantity must be a multiple of N" or "Price must be in multiples of X" — ideally caught at [rung 3](/broking-kyc/finix-broking-setup/oms/06-order-forward-path/) before sending |
| Instrument not available | "This contract is not available for trading today." |
| Order type not permitted | Should be impossible after [rung 4](/broking-kyc/finix-broking-setup/oms/06-order-forward-path/) — treat as a configuration defect |
| Member-level restriction | Operational escalation, not a client message |
| Session or state | "The market is not open for this segment." |

The rule implied by the last two rows: **any exchange rejection that the broker's own ladder should have prevented is a defect report**, and should be counted separately from genuine exchange-side rejections. A rising count there means the broker's validation has drifted from the exchange's rules.

## 3. Fills

| Aspect | Requirement |
|---|---|
| Identity | Each fill carries a trade identifier; store it, because it is the join key to the exchange trade file |
| Partial fills | Multiple fills per order; maintain cumulative filled quantity and weighted average price |
| Remaining quantity | Stays live, stays margined, stays counted against limits |
| Price | The traded price, not the order price |
| Timestamp | Exchange timestamp retained alongside the broker's receipt timestamp |
| Position update | Immediate and before risk utilisation |
| Margin recomputation | The post-trade position changes the requirement; recompute, do not assume the pre-trade estimate |
| Client view | Updated after position and risk, not before |
| Reconciliation | Real-time fills reconciled against the exchange trade file at end of session; the file is authoritative |

### 3.1 Propagation order

| Order | Target | Why this position |
|---|---|---|
| 1 | Order state | The replica of exchange truth |
| 2 | Position book | Everything downstream depends on it |
| 3 | Risk utilisation and available limit | Must know before the client can act again |
| 4 | Client view | Last, so the client never sees a position risk has not accounted for |
| 5 | Downstream event feed to the back office | Asynchronous, off the critical path |
| 6 | Audit trail | Guaranteed, asynchronous, never blocking |

<Aside type="note" title="The window between 4 and 3 is where over-limit orders get in">
If the client's screen updates before the risk engine's utilisation does, a fast client or an algorithm can submit the next order inside that window, and the risk engine will evaluate it against a stale utilisation. The window is usually milliseconds, which is exactly long enough for programmatic flow. Ordering the propagation so that risk is updated before the client is told is a one-line design decision that closes it.
</Aside>

## 4. Freezes

| Aspect | Detail |
|---|---|
| Cause | Order quantity or value above the exchange's freeze threshold for the instrument |
| State | Neither live nor rejected: pending exchange approval |
| Margin | Keep blocked while pending; the order may become live |
| Client representation | A distinct state with a distinct explanation — "this order is above the exchange's threshold and is awaiting exchange approval" |
| Outcome | Approval makes it live; rejection makes it terminal |
| Timing | Exchange-side process with its own timing; the client cannot be given a guaranteed time |
| Operational | Monitored by dealing; aged freezes escalated |
| Prevention | Known thresholds validated at [rung 8](/broking-kyc/finix-broking-setup/oms/06-order-forward-path/) where the broker can, so that large orders are flagged before submission |

## 5. Unsolicited and administrative messages

| Message | Cause | Handling |
|---|---|---|
| End-of-session cancellation | Day orders not executed | Bulk state transition; margin released; reflected before end-of-day processing |
| Cancellation on contract change | Lot size change, contract adjustment, corporate action | Client notified with the reason; broker-held intent on that instrument reviewed |
| Cancellation on instrument suspension | Instrument suspended intraday | Client notified; instrument blocked for new orders |
| Administrative cancellation | Exchange action | Operational escalation and client notification |
| Trade modification or cancellation | Exchange corrects a trade | Position, risk and back office all adjusted; this is rare and consequential |
| Member-level messages | Risk reduction mode, member restrictions | **Operational escalation**; may require stopping order flow |
| Market state messages | Session changes, halts, re-opens | Drive the session state machine, not just a log line |
| Band revision messages | Operating price range changes | **Applied**, not logged; see [attributes and validity](/broking-kyc/finix-broking-setup/oms/05-order-attributes-validity/#33-operating-price-range) |

| Rule | Detail |
|---|---|
| No message class is ignored | An unhandled class is silent divergence |
| Unknown message types alert | As with unknown rejection codes |
| Member-level messages reach a human | They are not order events; they are instructions to the firm |
| Market state drives behaviour | A halt message must stop order acceptance for that scope, not merely annotate the log |

## 6. Out-of-order and duplicate arrival

| Situation | Correct behaviour |
|---|---|
| Fill arrives before acknowledgement | Accept; do not require the acknowledgement first. The exchange's sequence is authoritative, not the broker's expectation |
| Duplicate message | Idempotent handling keyed on the exchange message identity |
| Terminal state arrives, then a non-terminal message | **Never regress.** A filled order does not become live again |
| Two terminal states | Investigate as an incident; this should not happen and indicates a mapping or sequencing defect |
| Message for an unknown order identifier | Do not discard. Store, alert, and reconcile — this is frequently the first visible sign of an order the broker does not know it sent |
| Sequence gap | Highest-priority incident; stop new flow in that segment and reconcile |

The second-to-last row is worth dwelling on. A message about an order the broker has no record of almost always means one of two things: an order was sent during a session break and never recorded, or the broker is receiving another member's traffic. The first is serious, the second is extremely serious, and discarding the message makes both invisible.

## 7. End of session

| Step | Detail |
|---|---|
| Day orders cancelled | By the exchange at end of session; reflected in the replica |
| Open orders in commodity good-till-date and good-till-cancelled | Survive; must be known and reviewed before the next session |
| Broker-held intent | Good Till Triggered, Stock SIP schedules and after-market queue carry over; verified at <abbr title="Beginning Of Day">BOD</abbr> |
| Margin release | All blocks released for cancelled orders |
| Final reconciliation | Order and trade counts and values against the exchange, before end-of-day processing begins |
| Handover | Open items passed to the end-of-day team, in writing |
| Commodity overlap | The equity end of session happens while the commodity market is still open; the two processes must not interfere |

## 8. Client communication

| Event | Communication |
|---|---|
| Acknowledgement | Order visible as live with exchange reference |
| Rejection | Mapped, actionable message |
| Partial fill | Executed quantity and remaining quantity both shown; the order is still working |
| Full fill | Executed quantity and average price |
| Trigger | The stop-loss has triggered and is now a live order |
| Freeze | Distinct explanation; awaiting exchange approval |
| Exchange cancellation | The reason, explicitly not presented as a client or broker cancellation |
| Cancellation rejected because filled | The true outcome stated plainly |
| `UNKNOWN` | Stated as unknown, with what the firm is doing about it |

| Principle | Reason |
|---|---|
| Never show a guess | An assumed state that turns out wrong is worse than an admitted uncertainty |
| Never show a code | Codes are for logs |
| Distinguish broker, exchange and client causation | It is the first question in any dispute |
| Match communication to the regulatory record | What the client was told must be reconstructible, and retained |

## 9. Intraday reconciliation

| Check | Frequency | Action on difference |
|---|---|---|
| Live order count against the exchange | Periodic through the session | Investigate immediately |
| Filled quantity and value by instrument | Periodic | Investigate immediately |
| Position by client against the firm's book | Periodic | Investigate; a position difference is a risk difference |
| Sequence continuity | Continuous | Stop new flow and reconcile |
| Orders in `UNKNOWN` | Continuous | Resolve before the session ends |
| Aged freezes | Continuous | Escalate |
| Unmapped rejection codes | Continuous | Engineering alert |

Divergence cost rises through the day. A morning difference is an investigation; the same difference at 15:35 collides with trade import, contract notes and obligation processing, all of which have deadlines that do not move.

## 11. Exception paths

| Situation | Response |
|---|---|
| Message for an unknown order identifier | Store, alert, reconcile; never discard |
| Two terminal states for one order | Incident; investigate mapping and sequencing |
| Fill arrives for a cancelled order | Exchange is authoritative; correct the replica and investigate the cancellation handling |
| Trade cancelled by the exchange after the client was told it executed | Client informed promptly and explicitly; position, risk and back office corrected; this is a high-sensitivity communication |
| Freeze pending at end of session | Resolve with the exchange; do not leave margin blocked indefinitely |
| Rejection rate spikes on one code | Treat as a configuration or protocol incident, not as client behaviour |
| Member-level risk reduction message received | Immediate escalation; may require stopping new orders |
| Sequence gap | Stop new flow in that segment and reconcile |
| Intraday position reconciliation differs | Stop increasing exposure for the affected clients until resolved |
| Orders left in `UNKNOWN` at session end | Must be resolved before end-of-day processing; escalate |

## Practical notes

- **Build the rejection code map before go-live and alert on unknowns.** New codes are the earliest signal of a protocol or rule change.
- **Count broker-preventable exchange rejections separately.** A rising count means your validation has drifted from the exchange's rules.
- **Never let the client view lead the risk engine.** It is a one-line ordering decision that closes a real exploit window.
- **Treat a message for an unknown order as serious.** It is either an order you did not record or traffic that is not yours.
- **Reconcile intraday.** The cost of a difference rises steeply after the close.
- **Give the freeze state its own words.** Clients handle "awaiting exchange approval" fine and handle silence badly.
- **Write the trade-cancellation communication template in advance.** It is rare, high-stress and high-sensitivity, and nobody writes well under those conditions.
