> **Why this page is structured this way:** Identifiers look like plumbing and behave like a control. Every order that reaches an exchange carries one, the exchange knows which identifiers a member has declared, and the member is obliged to declare them *before* use. That makes the identifier register one of the few artefacts where the firm's record and the regulator's record are directly comparable — which is exactly why it is an inspection favourite and exactly why it drifts. So the page covers the obligation first, then allocation, then the register, then the lifecycle events that cause drift, then the reconciliation that catches it.

## TL;DR

- **<abbr title="National Stock Exchange of India">NSE</abbr>: the trading member creates twelve-digit identifiers** for its users under the Non-NEAT Front End facility, and **must report the terminal details to the exchange before routing any order through such terminals**. Reporting is a precondition, not a follow-up.
- **The Computer-to-Computer Link facility is what permits an own front end at all**, and it is available only to trading members of NSE. Access to the trading system is through various modes of connectivity, each with a unique user identifier.
- **Administration goes through NSE-ENIT.** Applications for NEAT to <abbr title="Computer-to-Computer Link.">CTCL</abbr> conversion of user identifiers, and for non-NEAT user identifiers, are made through the ENIT interface per circular NSE/MSD/67755 dated 29 April 2025.
- **An identifier is not a login — it is an attribution.** It links an order to a person or a system, a location, and an entitlement. Sharing one destroys the attribution, which is the point of having it.
- **The register must reconcile with the exchange and with the directory.** Three records of the same population: the firm's register, the exchange's declared terminals, and the identity directory. Any two disagreeing is a finding.
- **Joiners, movers and leavers are the drift mechanism.** A dealer who leaves with their identifier still allocated and still reported is a live control gap that no system will report unless someone looks.
- **Algorithmic and programmatic flow needs its own identifier discipline** so that orders generated by a system are attributable to that system and its approval, not to whoever happened to start it.

## Conceptual overview

The reason exchanges care about identifiers is attribution. When an exchange sees a stream of orders, it needs to know not just which member sent them but which terminal, which location and — behind that — which person or system. That is what makes surveillance possible, what makes a disciplinary process possible, and what makes it possible to answer the question that follows every market incident: who did this, and under whose authority? The member's obligation to declare terminals before using them exists so that the exchange's map is complete before the orders start, not reconstructed afterwards.

For the firm, the same structure is the basis of its own controls. An identifier is where entitlement attaches: which segments this user may trade, which clients they may act for, what limits apply to their flow, which location they operate from. Because the identifier carries entitlement, sharing one is not a minor convenience — it collapses two people's authority into one indistinguishable stream, and it makes the audit trail unable to answer a question it is required to answer. The practical rule that follows is simple and frequently violated: one identifier, one actor, always.

The hard part is not setting this up; it is keeping it true. Identifier populations drift through ordinary business events — a dealer resigns, a branch closes, an authorised person is terminated, a test identifier created for certification is never withdrawn, a system is decommissioned but its credentials persist. None of these generate an alert. The only mechanism that catches them is periodic reconciliation between the firm's register, the exchange's record and the identity directory, with every difference investigated rather than explained away.

## 2. The NSE scheme

| Item | Detail |
|---|---|
| Facility | Computer-to-Computer Link, available only to NSE trading members, permitting use of the member's own front-end software |
| Access | Through various modes of connectivity, each with a unique user identifier |
| <abbr title="Non-NEAT Front End">NNF</abbr> identifiers | Trading members create **twelve-digit** identifiers for their users under the Non-NEAT Front End facility |
| Conversion | Members may convert NEAT identifiers to NNF and enable them for NNF products |
| **Reporting** | Terminal details must be reported to the exchange **before any order is routed** through such terminals |
| Administration route | NSE-ENIT, per NSE/MSD/67755 dated 29 April 2025 |
| Facilities | CTCL, internet-based trading, direct market access, wireless, algorithmic trading, smart order routing and application programming interface all operate against this identifier structure |

<Aside type="caution" title="Before, not after">
The obligation is to report before routing. A terminal brought into use on Monday and reported on Tuesday was in breach on Monday, and the breach is trivially demonstrable from the exchange's own data. Build the control as a hard gate: an identifier cannot be enabled for order routing in the <abbr title="Order Management System">OMS</abbr> until the register records a confirmed exchange reporting reference. Make the gate technical, because a procedural rule will eventually lose to an urgent Monday morning.
</Aside>

## 3. Identifier classes at Finix

| Class | Allocated to | Entitlement characteristics | Special controls |
|---|---|---|---|
| Dealer | A named, certified individual | Segments the dealer is certified for; client scope; limits | Certification gate; no sharing |
| Branch dealer | A named individual at a branch | As above, plus location | Location recorded and reported |
| Authorised person | A named individual at the authorised person | As above, with the member's responsibility | Tri-party agreement in force; monitoring obligation |
| Client internet | A client, for browser access | Own account only | Two-factor authentication |
| Client wireless | A client, for mobile access | Own account only | Two-factor authentication |
| Client API | An approved programmatic client | Own account only; rate-limited | Approval; per-client rate limits; kill switch |
| Algorithmic | A specific approved strategy | Strategy-scoped | Exchange approval reference recorded against the identifier |
| Risk operations | Risk staff, for square-off execution | Square-off scope only | Separate from any dealing identifier |
| Proprietary | Proprietary desk | Own-account only, segregated from client flow | Strict segregation from client identifiers |
| Test or certification | A named owner, for a stated purpose | Non-production or certification only | **Time-bound with a mandatory expiry**; the commonest drift source |

## 4. The identifier register

One register, one owner, one source of truth.

| Field | Content |
|---|---|
| Identifier | The exchange identifier, in its exchange-specific format |
| Exchange and segment | Which exchange, which segments enabled |
| Class | From the table above |
| Allocated to | Person identity from the central directory, or system identity |
| Certification reference | NISM certificate and its expiry, where the class requires one |
| Approval reference | Exchange facility or algorithm approval, where applicable |
| Location | Office, branch, authorised person premises, or data centre |
| Entitlements | Segments, client scope, limits, order types enabled |
| **Reported to exchange** | Date, reference, and confirmation |
| Enabled for routing | Boolean, gated on the reporting confirmation |
| Status | Active, suspended, withdrawn |
| Effective dates | From and to, append-only history |
| Last reconciled | Date of the last three-way reconciliation |
| Owner | The manager accountable for this identifier |

| Control | Requirement |
|---|---|
| Append-only history | Point-in-time answerable: who held this identifier on a given date |
| Maker-checker | On allocation, change of entitlement, and withdrawal |
| Certification gate | Identifier cannot be active for a certified function without a valid certificate |
| **Reporting gate** | Identifier cannot be enabled for routing without a confirmed exchange reporting reference |
| Retention | Eight-year floor, like all books and records |
| Review | Periodic entitlement recertification by the owner |

## 5. Lifecycle events and the drift they cause

| Event | What must happen | What usually happens | Control |
|---|---|---|---|
| Joiner | Allocate, certify, report, enable | Done correctly — joiners are visible | Role template |
| **Leaver** | Disable routing, withdraw at the exchange, remove directory access, close the register entry | **Identifier left active** | Same-day leaver checklist spanning all systems and both exchange and firm records |
| Mover between desks | Entitlements changed, old scope removed first | Entitlements accumulate | Remove-then-grant, never grant-alongside |
| Certification lapse | Identifier deactivated | Report generated, nobody acts | **Automatic deactivation on expiry**, not a report |
| Branch closure | Identifiers withdrawn, exchange updated | Identifiers linger | Branch-closure checklist |
| Authorised person terminated | Identifiers withdrawn, exchange updated, clients transitioned | Delay while commercials are argued | Termination checklist independent of the commercial dispute |
| Certification or test identifier created | Time-bound, expires automatically | Becomes permanent | Mandatory expiry date at creation; no indefinite test identifiers |
| Algorithm withdrawn | Identifier withdrawn with the approval | Identifier persists | Approval and identifier withdrawn together |
| System decommissioned | Credentials and identifier withdrawn | Credentials persist | Decommission checklist |
| Vendor support access | Time-bound, supervised, logged | Standing access | Just-in-time access only |

<Aside type="note" title="The leaver case is the one that matters">
Every other drift source is untidy. A departed dealer with a live, reported identifier is a person outside the firm associated with order-routing capability in the exchange's records. It is the single most consequential identifier defect and the easiest to prevent: one checklist, completed the same day, covering the OMS, the directory, each exchange's record and the register. Make completion evidenced, and sample-test it.
</Aside>

## 6. Three-way reconciliation

| Source | What it holds |
|---|---|
| A. The firm's identifier register | What the firm believes it has allocated |
| B. The exchange's record of reported terminals | What the exchange believes the firm has declared |
| C. The identity directory and OMS entitlements | What is actually capable of placing an order |

| Difference | Meaning | Severity |
|---|---|---|
| In C but not in A | An identifier can trade that the register does not know about | **Critical** — unregistered trading capability |
| In C but not in B | An identifier can trade that was never reported | **Critical** — direct breach of the reporting obligation |
| In A and B but not in C | Reported but not enabled | Low, but tidy it: the exchange's map is wrong |
| In B but not in A | The exchange believes in an identifier the firm does not track | High — register incomplete |
| In A but not in B | Allocated but unreported | High — must not be enabled for routing |
| Active in A, holder left per the directory | Leaver failure | **Critical** |
| Active in A, certificate expired | Certification failure | High |
| Test identifier past its expiry | Drift | Medium, and a process signal |

| Reconciliation control | Requirement |
|---|---|
| Frequency | Monthly at minimum; weekly during the first quarter after go-live |
| Automation | Differences generated automatically, not assembled by hand |
| Disposition | Every difference investigated, with an outcome recorded — never "known difference" without a reason and a date |
| Escalation | Critical differences to compliance same day |
| Evidence | Reconciliation output retained on the records floor |

## 9. Exception paths

| Situation | Response |
|---|---|
| Identifier found routing without a reporting confirmation | Disable immediately, report to the exchange, record as a control failure and assess disclosure |
| Identifier sharing detected | Disable, investigate, and treat as a conduct matter — the audit trail for the affected period is compromised |
| Dealer certificate expired and orders were placed | Disable, quantify the period and the orders, escalate to compliance, assess reporting |
| Leaver's identifier found active | Disable same day, reconcile the activity since departure, record as a control failure |
| Register and exchange record disagree | Treat the capability in the OMS as the risk-relevant truth; align both records; investigate the cause |
| Test identifier found in production | Disable; investigate how certification access reached production |
| Authorised person terminated but identifiers live | Disable immediately; the commercial dispute is separate from the control |
| Algorithm identifier active without a current approval | Disable; this is an unapproved algorithmic trading exposure |
| Urgent need to trade before reporting completes | **There is no exception.** Use an existing reported identifier or do not trade |

## Practical notes

- **Gate routing on the reporting reference, in code.** Procedural rules lose to urgency; a gate does not.
- **Deactivate on certificate expiry automatically.** A report that a certificate has lapsed is a report that somebody must act on; deactivation is the act.
- **Give every test identifier an expiry at creation.** Certification identifiers surviving into production is a recurring pattern across the industry.
- **Reconcile three ways, not two.** Register against exchange catches reporting gaps; register against the directory catches leaver gaps. You need both.
- **Record the location.** Identifier location is part of what the exchange knows, and branch and authorised-person moves are easy to miss.
- **Keep proprietary identifiers strictly separate.** Conflating own and client flow at identifier level undermines every downstream segregation control.
- **Treat the register as a book and record.** Eight-year retention, point-in-time answerable, maker-checker.
