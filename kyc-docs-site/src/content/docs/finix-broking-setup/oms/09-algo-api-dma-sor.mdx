> **Why this page is structured this way:** The regulatory substance of the retail algorithmic framework is already set out in depth elsewhere on this site, so this page does not repeat it. What it does instead is translate it into the things a build team configures and an operations team runs: the registry, the tag that must be on every order, the thresholds that reclassify a client, the controls that must exist before the facility is switched on, and the kill switch that must work when it is needed. Each facility is treated separately because they have different approvals, different clients and different failure modes, and they are frequently conflated.

## TL;DR

- **The threshold that reclassifies a client is ten orders per second.** Retail application programming interface access at or below that rate is ordinary access; above it, the flow is treated as algorithmic and must be registered with a **unique algorithm identifier tagged to every order**.
- **The broker is the principal and the algorithm provider is the agent.** The broker is accountable for any algorithm misuse through its interfaces. That is an architectural statement, not a commercial one: the controls have to live in the broker's path because the liability does.
- **Every algorithmic order carries a tag, and the tag is validated.** Pre-trade controls include **NNF terminal identifier to algorithm identifier validation**, so an untagged or mis-tagged algorithmic order is a control failure that the exchange can see.
- **Algorithm market orders have a pre-emptive cancellation control** introduced to prevent runaway market orders — a direct response to the failure mode where an automated strategy issues market orders into a thin book.
- **White-box and black-box classification drives the approval path.** Deterministic execution logic is treated differently from predictive or model-driven logic whose behaviour is not fully transparent.
- **Approval is per algorithm, per exchange, per segment, per broker.** There is no portable approval, and the registry has to reflect that dimensionality or it will drift.
- **The kill switch must be scoped, tested and fast** — per algorithm, per client, per identifier, per segment — and it must be exercised in a drill, because it is used at the worst moment by someone who is not calm.
- **Direct market access and smart order routing are deferred at Finix**, deliberately, because each carries its own approval, its own control set and its own client population, and launching four programmatic facilities at once is how a firm discovers it monitored none of them.

## Conceptual overview

Programmatic access changes the order path in two ways that matter more than the obvious one. The obvious change is rate: a system can generate more orders faster than a person, so capacity and rate limiting become functional requirements rather than hygiene. The two deeper changes are about attribution and about failure shape. Attribution, because an order generated by a strategy running at a vendor, on behalf of a client, through a broker's interface, has four parties in its history, and the regulatory framework requires that chain to be reconstructible from the order itself — hence the tag. Failure shape, because automated systems fail by repeating, not by stopping. A human who misprices an order places one bad order; a strategy that misprices places thousands, and it does so faster than anyone can watch.

That is why the control set for this facility is different in kind from the rest of the order path. Everywhere else, controls are about whether a particular order is acceptable. Here, controls are also about whether a *pattern* is acceptable — order rate, order-to-trade ratio, cancel rate, repeated rejection — and about having a mechanism to stop a pattern immediately without stopping everything else. A firm that enables programmatic access with per-order controls and no per-pattern controls has built a system that will faithfully validate each of ten thousand wrong orders.

The third consideration is that the broker's position as principal removes the comfortable option of treating a vendor's algorithm as the vendor's problem. The broker registers it, the broker tags its orders, the broker's audit trail must trace every tagged order back to the registered algorithm and the interface vendor, and the broker answers for misuse. In practice this means the empanelment process is a control, not a commercial formality: what the firm accepts into its registry it owns.

## 1. Regulatory framework

The substance is covered in depth at [retail algo framework](/broking-kyc/deep-dives/trading-day/retail-algo-framework/). The operative instruments:

- **[SEBI/HO/MIRSD/MIRSD-PoD/P/CIR/2025/0000013](/broking-kyc/reference/circulars/sebi-mirsd/#sebihomirsdmirsd-podpcir20250000013)** (4 February 2025) — Safer Participation of Retail Investors in Algorithmic Trading; originally effective 1 August 2025, subsequently extended by a SEBI timeline extension circular of July 2025.
- **[NSE/INVG/66524](/broking-kyc/reference/circulars/nse/#nseinvg66524)** (5 February 2025) → **[NSE/INVG/67858](/broking-kyc/reference/circulars/nse/#nseinvg67858)** (5 May 2025) → **[NSE/INVG/69255](/broking-kyc/reference/circulars/nse/#nseinvg69255)** (22 July 2025) — the NSE operational implementation chain, including the principal–agent accountability model and the five-year audit-trail retention for algorithmic orders.
- **[NSE/FAOP/69296](/broking-kyc/reference/circulars/nse/#nsefaop69296)** (August 2025) — pre-trade controls hardening: algorithm market order pre-emptive cancellation, and NNF terminal identifier to algorithm identifier validation.
- **[NSE/INSP/64438](/broking-kyc/reference/circulars/nse/#nseinsp64438)** and **[NSE/INSP/70900](/broking-kyc/reference/circulars/nse/#nseinsp70900)** — Type III system audit requirements for in-house algorithms.
- **[SEBI (Stock Brokers) Regulations, 2026](/broking-kyc/finix-broking-setup/setup/02-sebi-registration-2026/)** — Chapter IV fraud prevention and detection, which covers surveillance over the firm's own systems including automated order flow. `[not yet in index]`
- **Exchange facility approval frameworks** for direct market access and smart order routing, each separate from algorithmic approval.

<Aside type="caution" title="Audit trail retention: two clocks">
The algorithmic framework specifies five-year audit-trail retention for algorithm-tagged orders. Regulation 16 of the 2026 regulations sets a records floor of not less than eight years. The longer obligation governs the record. Configure retention to the eight-year floor and treat the five-year figure as a minimum specific to this framework, not as the applicable period.
</Aside>

## 2. The four facilities

| Facility | What it is | Client population | Approval | Finix at launch |
|---|---|---|---|---|
| **Application programming interface** | Programmatic order entry by a client for their own account | Retail and HNI clients, and vendors acting for them | Exchange facility approval; higher base minimum capital tier | **Enabled** |
| **Algorithmic trading** | Order generation without a human acting per order | API clients above the threshold; vendor strategies; in-house | Per algorithm, per exchange, per segment; Type III audit for in-house | **Enabled, registry-gated** |
| **Direct market access** | An institutional client routes its own orders through the broker's infrastructure | Institutional | Separate approval; client agreements | **Deferred** |
| **Smart order routing** | Routing between exchanges for the better price | Any client, as a broker service | Separate approval; demonstrable best-execution logic | **Deferred** |

### 2.1 Why direct market access and smart order routing are deferred

Each adds a distinct client population, a distinct control set and a distinct monitoring obligation. Direct market access brings institutional clients whose flow characteristics, agreements and risk controls differ from retail. Smart order routing introduces a routing decision the firm must be able to justify order by order as best execution, with the data to prove it. Deferring both is a capacity decision rather than a technical one: launching four programmatic facilities simultaneously means monitoring none of them properly in the first quarter. The decision is recorded with a review trigger rather than left implicit.

## 3. Classification and the threshold

| Dimension | Values | Consequence |
|---|---|---|
| **Order rate** | At or below **ten orders per second**; above ten orders per second | Above the threshold, the flow is treated as algorithmic, must be registered, and every order must carry a unique algorithm identifier |
| **Logic transparency** | White-box — deterministic execution logic; black-box — predictive or model-driven, logic not fully transparent | Drives the approval path and the diligence depth |
| **Origin** | In-house; empanelled vendor | In-house requires a broker-level Type III system audit; vendor algorithms must be in the broker's registered list |
| **Client frequency class** | Low, medium, high frequency | Drives monitoring intensity and control thresholds |

| Implementation requirement | Detail |
|---|---|
| Rate measurement | Measured continuously per client and per identifier, at the resolution the threshold implies |
| Threshold approach | Alert **before** the threshold, not at it; a client drifting toward reclassification should be contacted, not surprised |
| Reclassification | A defined process: notify the client, register the algorithm, issue the identifier, enable tagging — never a silent switch |
| Enforcement | Flow above the threshold without a registered algorithm identifier must be **blocked**, not merely flagged |

## 4. The algorithm registry

| Field | Content |
|---|---|
| Algorithm identifier | The unique identifier tagged to every order from this algorithm |
| Name and description | What it does, in terms a non-engineer can assess |
| Classification | White-box or black-box |
| Origin | In-house, or the empanelled vendor's identity |
| Approval references | Per exchange and per segment, with dates |
| Status | Pending, approved, suspended, withdrawn |
| Permitted exchanges and segments | Explicit; no implicit extension |
| Permitted clients | Which clients may run it |
| Permitted order types | Often narrower than the client's general entitlement |
| Rate limits | Orders per second, per minute, per day |
| Position and value limits | Strategy-scoped, separate from the client's general limits |
| Terminal identifier mapping | For NNF-to-algorithm-identifier validation |
| Static IP | Where required for attribution |
| Audit-trail requirements | Confirmed and configured |
| Kill-switch scope | How this algorithm is stopped |
| Owner | The accountable person inside the firm |
| Last review | Date and outcome |

| Control | Requirement |
|---|---|
| Registry is the gate | An algorithm not in the registry with an approved status cannot place an order; enforced in code, not in process |
| Per-exchange, per-segment | An approval for one segment does not enable another |
| Withdrawal is immediate | Withdrawing an approval withdraws the identifier's ability to trade, same moment |
| Review | Periodic, with the vendor's own changes assessed |
| Change control | A material change to an algorithm is a new approval question, not a deployment |

## 5. Tagging and validation

| Control | Detail |
|---|---|
| Algorithm identifier on every order | Every order generated by a registered algorithm carries its identifier |
| **NNF terminal identifier to algorithm identifier validation** | Enforced as a pre-trade control; the terminal and the algorithm must match the registered mapping |
| Untagged algorithmic flow | **Blocked** |
| Mis-tagged flow | Blocked and alerted; a mis-tag is a control failure, not a data-quality issue |
| **Algorithm market order pre-emptive cancellation** | A control against runaway market orders from automated strategies |
| Audit trail | Every tagged order traceable to its registered algorithm and the interface vendor; retained on the eight-year floor |
| Static IP | Where required, orders validated against the registered address |
| Reconciliation | Tagged order counts reconciled against the registry's expectations; an algorithm trading more than it should is visible only if someone looks |

## 6. Pre-trade controls for programmatic flow

These sit on top of the ordinary [forward path](/broking-kyc/finix-broking-setup/oms/06-order-forward-path/), not instead of it.

| Control | Scope | Default behaviour on breach |
|---|---|---|
| Orders per second | Per client, per identifier, per algorithm | Throttle, then block that scope |
| Orders per minute and per day | Same | Block that scope |
| Order-to-trade ratio | Per client and per algorithm | Alert, then block |
| Cancel-to-order ratio | Same | Alert, then block |
| Consecutive rejection count | Per algorithm | **Block** — repeated rejection is the classic runaway signature |
| Market order controls | Per algorithm | Pre-emptive cancellation; consider blocking market orders entirely for automated flow |
| Price collar | Tighter than for manual flow | Reject |
| Maximum order value and quantity | Per algorithm | Reject |
| Net and gross position limits | Per algorithm, separate from the client's general limits | Reject |
| Daily loss limit | Per algorithm and per client | **Kill the algorithm** |
| Self-trade prevention | Per client | Reject |
| Duplicate detection | Per client reference | Suppress and alert |
| Instrument whitelist | Per algorithm | Reject outside it |
| Session-time restrictions | Per algorithm | Reject outside permitted windows |

<Aside type="note" title="Consecutive rejections are the best runaway detector you have">
A strategy that has lost its connection to reality — stale reference data, a sign error, a mis-parsed instrument — typically produces a stream of orders that the exchange rejects for the same reason. Rate limits may not catch it if the rate is moderate, and value limits will not catch it if each order is small. A consecutive-rejection counter with a low ceiling catches it in seconds, costs nothing, and has almost no false-positive cost because a correctly functioning strategy does not generate repeated identical rejections.
</Aside>

## 7. The kill switch

| Scope | Who can invoke | Expected effect |
|---|---|---|
| One algorithm | Risk, dealing, technology | New orders stopped; resting orders cancelled per policy |
| One client's programmatic access | Risk | All automated flow for that client stopped |
| One identifier | Risk, technology | That terminal or system stopped |
| All algorithmic flow in a segment | Senior risk | Segment-scoped stop |
| All programmatic access | Senior risk, two-person | Everything automated stopped; manual flow continues |

| Requirement | Detail |
|---|---|
| Speed | Effective within seconds; a kill switch that takes minutes is not one |
| Resting orders | Policy decides whether a kill cancels resting orders; **decide in advance**, configure it, and tell clients |
| Independence | Must work when the algorithm's own systems are unresponsive — it is the broker's control, not the strategy's |
| Logging | Who, when, scope, reason, and the resulting order list |
| Client communication | Affected clients told promptly, with the reason |
| **Rehearsal** | Exercised in a drill at least annually, and after any material change |
| Automatic triggers | Daily loss limit, consecutive rejections, rate-limit persistence — these should fire the kill switch without waiting for a human |

## 8. Vendor empanelment

| Step | Content |
|---|---|
| 1. Assessment | What the algorithm does; white-box or black-box; the vendor's own controls and testing |
| 2. Classification | Which approval path applies |
| 3. Diligence | The vendor's security posture, change management, incident history and support model |
| 4. Contract | Obligations flowed down, including cooperation with exchange and regulator enquiries and a defined change-notification lead time |
| 5. Registration | With the broker, then with each exchange and segment |
| 6. Controls | Rate, position, value, instrument and loss limits set per algorithm before enablement |
| 7. Testing | In a simulated environment, and in a mock session where exchange behaviour matters |
| 8. Enablement | Registry status set to approved; tagging and validation verified with live traffic at low volume |
| 9. Monitoring | Ongoing, with the pattern controls from section 6 |
| 10. Review | Periodic; vendor changes trigger reassessment |

Because the broker is the principal, step 3 is a real control rather than a formality. The firm is accountable for misuse of its interfaces by an agent it empanelled.

## 9. Direct market access and smart order routing, when enabled

| Facility | Additional requirements |
|---|---|
| Direct market access | Separate exchange approval; client agreements establishing the arrangement; risk controls applied to client-routed orders at the broker's layer, not delegated; per-client identifiers; order attribution to the originating client; monitoring appropriate to institutional flow |
| Smart order routing | Separate exchange approval; **documented, demonstrable best-execution logic**; the data to show, order by order, why a venue was chosen; client disclosure; handling of a venue being unavailable; no routing that disadvantages a client for the broker's benefit |

The smart order routing requirement to demonstrate best execution order by order is a data-retention obligation as much as a logic one: the firm must keep, for the retention period, the market state it observed and the decision it made.

## 11. Exception paths

| Situation | Response |
|---|---|
| Untagged order above the threshold | Blocked; client contacted; registration process started; investigate how the flow grew unnoticed |
| Algorithm trading in an unapproved segment | Blocked by the registry gate; if it got through, treat as a severity-one control failure |
| Consecutive rejections from one algorithm | Automatic kill; investigate before re-enabling |
| Daily loss limit breached | Automatic kill; client and risk informed |
| Vendor changes an algorithm without notice | Suspend the registry entry; reassess; the contract should make notice an obligation |
| Kill switch invoked but orders continue | **Severity one.** Stop the identifier at the gateway and, if necessary, the session |
| Client requests a higher rate limit | Assess against classification; above the threshold it is a registration question, not a limit question |
| Static IP mismatch | Block and investigate; this is an attribution control |
| Runaway detected but the client is unreachable | Act first, inform afterwards; the firm is the principal |
| Exchange queries an algorithm's behaviour | The audit trail must answer within the firm, not via the vendor; this is why the trail is the broker's obligation |

## Practical notes

- **Make the registry a hard gate in code.** Process-based gating fails the first time someone is in a hurry.
- **Alert before the threshold, not at it.** A client reclassified without warning is a complaint and a relationship problem; a client contacted at eight orders per second is a conversation.
- **Build the consecutive-rejection counter first.** It is the cheapest high-value control on this page.
- **Decide the resting-order question for the kill switch before launch** and disclose it. Clients can accept either behaviour; they cannot accept discovering it mid-incident.
- **Rehearse the kill switch.** Annually at minimum, and after any change to the order path.
- **Retain to eight years, not five.** The longer obligation governs.
- **Do not launch all four facilities together.** Monitoring capacity, not technical capability, is the constraint.
- **Treat empanelment as a control.** What enters the registry, the firm owns.
