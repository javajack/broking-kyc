> **Why this page exists:** Configuration discussed across ten pages is configuration nobody can audit. This page is the single table an engineer configures from, a reviewer approves against and an inspector is shown. The classification column is the one that matters most: a regulatory value needs a circular, an exchange-set value needs a refresh mechanism, and a discretionary value needs an approved policy — and misclassifying any of them is itself a finding.

## TL;DR

- **Three classes, three evidence requirements.** Regulatory values trace to a regulation or circular. Exchange-set values trace to a circular *and* a named ingestion job with a staleness behaviour. Discretionary values trace to an approved policy and an approver.
- **Scope resolution is most-specific-wins** — client, client group, product, segment, exchange, global — and every key must have a global default so resolution always terminates.
- **Two hard gates bind configuration to reality**: an order type cannot be enabled unless the certification record contains it, and an identifier cannot route unless the register holds a confirmed exchange reporting reference.
- **Some values must never change mid-session.** Anything that can turn a compliant client into a non-compliant one — tightening a limit, lowering a square-off trigger, changing a cut-off — takes effect at a boundary.
- **The dangerous defaults are the permissive ones.** Risk timeout, stale-data behaviour, audit-write failure and untagged algorithmic flow all have a safe setting that an engineer optimising for availability would not choose.
- **Configuration is retained on the eight-year floor** and must be point-in-time answerable: what was key K for scope S at timestamp T.

## 1. How to read this reference

| Column | Meaning |
|---|---|
| Key | Named per the [configuration convention](/broking-kyc/finix-broking-setup/stack/environments-config-baseline/#2-configuration-key-convention) |
| Finix default | The value this manual assumes |
| Class | **R** regulatory · **E** exchange-set · **D** discretionary |
| Mid-session | Whether the value may change while a market is open |
| Failure mode | What goes wrong if the value is wrong |

Scope suffixes used below: `<exchange>` NSE, BSE, MCX · `<segment>` CM, FO, CD, COM · `<channel>` terminal, web, mobile, api, algo · `<class>` identifier class · `<algo>` algorithm identifier.

## 11. The gates

Two configuration relationships are enforced as gates rather than as review items, because both have failed in the industry when left procedural.

| Gate | Rule | Enforcement |
|---|---|---|
| **Certification gate** | `finix.oms.ordertype.enabled.*` ⊆ the certification record, per exchange, segment and channel | Scheduled automated diff; any difference alerts and the extra type is disabled |
| **Reporting gate** | An identifier may route only if the register holds a confirmed exchange reporting reference | Checked at rung 2 of the [forward path](/broking-kyc/finix-broking-setup/oms/06-order-forward-path/) |

<Aside type="caution" title="The defaults that an availability-minded engineer would get wrong">
Six values on this page have a safe setting that conflicts with the instinct to keep the system up: `risk.timeout_action` = reject; `marketdata.stale_action` = block; `audit.write_failure_action` = stop if sustained; `conn.sequence_gap_action` = stop and reconcile; `conn.resume_requires_recon` = true; `algo.above_threshold_untagged_action` = block. Each trades availability for correctness, and each is right. Record the reasoning next to the value, because the first person to meet one of them during an incident will want to change it.
</Aside>

## 12. Change control

| Requirement | Detail |
|---|---|
| Versioning | Append-only, with effective-from and effective-to timestamps |
| Attribution | Author, approver, reason; approver never the author for R and E class |
| Maker-checker | Mandatory for every value on this page |
| Point-in-time query | What was key K for scope S at timestamp T, without restore |
| Mid-session rule | Any change that can turn a compliant client into a non-compliant one takes effect at a boundary |
| Retention | Eight-year floor, as a book and record |
| Daily reconciliation | Deployed configuration diffed against the approved register, exceptions reported |
| Emergency change | Documented break-glass with post-hoc approval inside one business day, logged distinctly |

## 13. Review cadence

| Class | Trigger |
|---|---|
| Regulatory | On any circular or regulation change affecting the value |
| Exchange-set | Continuously by the ingestion job; the *configuration of the job* reviewed quarterly |
| Discretionary | At least annually, and on any policy change |
| Certification-gated | At every certification cycle |
| Protocol versions | On every exchange protocol circular |
| Rate and collar values | Quarterly against observed rejection and incident data |
| Kill-switch and bulk-cancel scopes | After every drill |
