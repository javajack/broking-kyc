> **Why this page is structured this way:** Connectivity is where "it works on <abbr title="National Stock Exchange of India">NSE</abbr>" stops generalising. Each exchange has a different access model, a different session concept, a different per-segment topology and a different upgrade cadence, and those differences determine how many deployments you run, how many runbooks you write and how many certification tracks you plan. So the page treats each exchange separately and in full, then pulls out the cross-cutting concerns — sessions, sequencing, versioning, capacity — that have to be solved once but configured three times.

## TL;DR

- **NSE: Computer-to-Computer Link, available only to NSE trading members**, lets the member use its own front end. Access is by unique user identifier over a wide area network on TCP/IP, with interactive TCP/IP connectivity for user-specific messages to and from the exchange. The front end may connect through middleware called the **Trading Access Point**.
- **NSE's Non-NEAT Front End is the protocol family**, with specifications published and versioned **per segment** — the commodity, futures and options, and securities lending and borrowing protocol documents are separate documents with separate version numbers. There is no single <abbr title="Non-NEAT Front End">NNF</abbr> specification.
- **<abbr title="BSE Limited (formerly Bombay Stock Exchange)">BSE</abbr>: the Enhanced Trading Interface, BSE <abbr title="Enhanced Trading Interface">ETI</abbr>**, which replaced the now-discontinued IML. ETI is **session-oriented**, and **a separate session is required per segment** while the **participant identifier stays the same across segments**. API versions are **mandated by the exchange**.
- **<abbr title="Multi Commodity Exchange of India">MCX</abbr>: its own member protocol**, with published guidance referring to ISDN or other internet connectivity with firewalls. Confirm the current approved options; the long session to 23:30 makes connectivity monitoring an evening activity.
- **Protocol upgrades are certification events, not deployments.** When an exchange versions a protocol, the member re-certifies. Version tracking per interface with a known upgrade window belongs in the [configuration register](/broking-kyc/finix-broking-setup/stack/environments-config-baseline/).
- **Sequence continuity is the health signal that matters.** A connection that is up but has a sequence gap is in a worse state than one that is down, because it looks healthy while the firm's view of its own orders diverges from the exchange's.
- **Market data is a separate concern from order flow** and must be capacity-planned separately; a volatility burst multiplies tick rates without touching order rates.

## Conceptual overview

Every exchange connection is really three things bundled together: a transport, a session, and a message grammar. The transport is the least interesting — it is a network link with the usual properties, and it fails in the usual ways. The session is where the exchange's model shows through: what constitutes a login, what state the exchange holds for the member, what happens on disconnection, and whether orders survive. The message grammar is where the per-exchange and per-segment differences live, and it is versioned by the exchange on its own schedule.

The practical consequence of bundling them is that a single failure mode — "connectivity down" — actually covers several very different situations with very different responses. A transport failure with the session intact at the exchange means the exchange may still hold live orders. A session logout means the exchange's view of the member has changed. A sequence gap with the transport healthy means messages were lost in a way neither side has yet noticed. These require different operational responses, and a monitoring system that reports a single boolean cannot distinguish them. That is why the [integration contract matrix](/broking-kyc/finix-broking-setup/stack/integration-contract-matrix/#2-order-path--the-real-time-band) treats sequence continuity as a distinct detection mechanism rather than folding it into connection state.

The second structural point is the per-segment multiplication. On NSE, segments are largely enabled on a shared connectivity stack. On BSE, each segment needs its own ETI session, so session establishment, monitoring, failover and certification all apply per segment while the participant identifier stays common. That is a smaller difference than three separate integrations and a larger one than a configuration flag — and teams that model BSE as “NSE with different field names” discover it during certification, which is the expensive moment.

## 1. Regulatory and documentary framework

- **NSE platform services documentation** — Computer-to-Computer Link, Non-NEAT Front End, user identifier and <abbr title="Computer-to-Computer Link.">CTCL</abbr> identifier material, and the segment-wise NNF protocol specifications. These are the operative documents, published and versioned by the exchange. `[not yet in index]`
- **NSE/MSD/67755** (29 April 2025) — applications for NEAT to CTCL conversion of user identifiers and for non-NEAT user identifiers, through NSE-ENIT. `[not yet in index]`
- **BSE ETI API manual and BOLT Plus connectivity manual** — published and versioned by the exchange, with **mandated API versions** applied across segments. The legacy IML interface is discontinued. `[not yet in index]`
- **MCX connectivity and membership guidance** — including the compliance guide. `[not yet in index]`
- **[<abbr title="Securities and Exchange Board of India">SEBI</abbr> (Stock Brokers) Regulations, 2026](/broking-kyc/finix-broking-setup/setup/02-sebi-registration-2026/)** — regulation 18(5) cyber security and cyber resilience, which governs how these links are secured. `[not yet in index]`
- **Facility approval frameworks** — internet-based trading, wireless, direct market access, algorithmic trading, smart order routing and application programming interface access all ride on this connectivity and each is separately approved. See [algo, API, DMA and <abbr title="Smart Order Routing">SOR</abbr>](/broking-kyc/finix-broking-setup/oms/09-algo-api-dma-sor/).

<Aside type="caution" title="This page does not reproduce protocol layouts">
Message structures, field layouts and tag definitions live in the exchange's own protocol documents, which are supplied under agreement and are versioned. This page describes what the connectivity *is* and how it behaves operationally, and names the document to get the layout from. Building from a third-party description of an exchange protocol is how field-level defects enter a stack.

## 2. NSE

| Aspect | Detail |
|---|---|
| Facility | Computer-to-Computer Link, available only to trading members of NSE, allowing the member to use its own trading front-end software |
| Access model | The exchange trading system is accessed through various modes of connectivity, each with a unique user identifier |
| Protocol family | Non-NEAT Front End; members may convert NEAT identifiers to NNF and enable them for NNF products |
| Protocol documents | Published **per segment** and versioned — for example separate commodity and securities lending and borrowing protocol documents with their own version numbers |
| Transport | Wide area network over TCP/IP |
| Interactive connectivity | TCP/IP for user-specific messages to and from the exchange |
| Middleware | The trading front end may connect through a middleware application called the **Trading Access Point** |
| Identifiers | Trading members create **twelve-digit identifiers** for users under the NNF facility |
| Reporting | Terminal details must be reported to the exchange **before routing any order** through such terminals |
| Identifier administration | Through NSE-ENIT, per NSE/MSD/67755 dated 29 April 2025 |
| Member portal | ENIT at `enit.nseindia.com/MemberPortal/` |
| Facilities riding on it | CTCL, internet-based trading, direct market access, securities trading through wireless technology, algorithmic trading, smart order routing, application programming interface |

### 2.1 The Trading Access Point decision

| Option | Characteristics | When it makes sense |
|---|---|---|
| Direct connection from the front end | Fewer hops, fewer components to monitor | Where the vendor supports it and the operational model is simple |
| Via the Trading Access Point | An additional middleware layer the front end connects through | Where it simplifies connection management across users and segments, or where the vendor's architecture assumes it |

Whichever is chosen, it is an architectural fact to be documented, monitored and included in the latency budget — not an implementation detail. A middleware hop is a hop in [the budget](/broking-kyc/finix-broking-setup/oms/01-oms-architecture/#3-latency-budget) and a component in the failure analysis.

## 3. BSE

| Aspect | Detail |
|---|---|
| Interface | **BSE ETI (Enhanced Trading Interface)**, the current interactive interface to BOLT Plus |
| Legacy | **IML is discontinued** |
| Nature | **Session-oriented**; high-performance, low-latency; full trading, drop copy and risk alerts |
| **Session model** | **A separate session per segment** |
| **Participant identifier** | **Common across segments** |
| Segments | Equity and equity derivatives in production, simulation and disaster recovery; currency and commodity derivatives also supported |
| **Versioning** | **Exchange-mandated ETI API versions**, applied across segments |
| Documents | ETI API manual; BOLT Plus connectivity manual |

### 3.1 What per-segment sessions cost

Less than three separate integrations, more than a configuration flag.

| Dimension | Consequence |
|---|---|
| Provisioning | Connectivity provisioned once; **sessions established per segment** |
| Session management | Establish, monitor and recover per segment |
| Monitoring | Per-segment session state, sequence continuity and latency, with per-segment alerting |
| Failover | Exercised per segment session |
| Capacity | Message rates considered per segment |
| **Version upgrades** | **Exchange-mandated**, scheduled, and a certification event |
| **Certification** | **Per segment**; success on one segment does not transfer |
| Runbooks | Start, stop, recover and verify procedures that name the segment |
| Incident scope | **Segment-scoped** — "BSE is down" is rarely the right first statement |

<Aside type="tip" title="Exploit the segment scoping">
Independent sessions per segment give real isolation: an equity derivatives session problem does not have to stop equity trading. Collecting that benefit requires segment-scoped health indicators, segment-scoped client messaging and the ability to stop one segment cleanly while the others run. A firm that aggregates the segments into one "BSE status" pays for the session management and keeps none of the isolation.
</Aside>

## 4. MCX

| Aspect | Detail |
|---|---|
| Access model | MCX member protocol |
| Connectivity guidance | Published guidance refers to ISDN or any other type of internet connectivity with firewalls; **confirm the current approved connectivity options with the exchange** |
| Session hours | Non-agricultural commodities 09:00 to 23:30, or 23:55 during United States daylight saving; select agricultural such as cotton to 21:00; other agricultural to 17:00 |
| Operational consequence | Connectivity monitoring, incident response and vendor support all extend into the evening |
| Delivery-related messaging | Tender and delivery intentions handled through <abbr title="Multi Commodity Exchange Clearing Corporation Limited">MCXCCL</abbr> eClear, accepted until 19:30 on tender days — a separate system with its own availability requirement |

### 4.1 What the long session changes

| Area | Change |
|---|---|
| Monitoring | Evening coverage with the same alerting standards as the day session |
| Maintenance windows | Compress to a narrow overnight window shared with batch processing |
| Patching | Must not collide with the commodity session or the equity end-of-day |
| Vendor support | Support hours must cover to 23:30; confirm contractually |
| Incident escalation | An evening escalation path with named people, not best-effort |
| Daylight saving | Two scheduled changes a year to the close time, which must flow into monitoring, rotas and batch scheduling |

## 5. Session management

| Concept | Design |
|---|---|
| Establishment | At <abbr title="Beginning Of Day">BOD</abbr>, per exchange and per segment instance, before the market opens; part of the [BOD runbook](/broking-kyc/finix-broking-setup/daily-ops/01-bod-runbook/) |
| Authentication | Per exchange mechanism, with credentials held in the managed secret store |
| Heartbeat | Per protocol requirement, with an alert on a missed heartbeat rather than on a missed window of heartbeats |
| Sequencing | Continuous tracking; **a gap is an incident** |
| Disconnection | Classified: transport loss, session logout, application failure — different responses |
| Reconnection | Automatic with bounded attempts and backoff, then human escalation |
| State after reconnection | **Reconcile against the exchange before accepting new order flow in that segment** |
| End of session | Orderly logout; the exchange's end-of-session behaviour for live orders is protocol-defined and must be reflected in the order state machine |
| Multiple sessions | Where permitted, deliberate and documented; sequence tracking is per session |

### 5.1 Disconnection classification

| Class | Symptom | Exchange may hold live orders | Response |
|---|---|---|---|
| Transport loss | Link down, no clean logout | **Yes** | Reconnect, reconcile, do not assume order state |
| Session logout, clean | Exchange acknowledged logout | Protocol-defined | Re-establish, reconcile |
| Application failure | Process down, link up | **Yes** | Restart, reconcile |
| Sequence gap | Link healthy, numbering broken | **Yes, and divergence already exists** | Treat as the most serious class: stop new flow, reconcile |
| Exchange-side unavailability | Exchange-announced | Per exchange communication | Follow exchange instruction; communicate to clients |

## 6. Protocol versioning

| Control | Requirement |
|---|---|
| Version register | Current version per exchange, per segment, per instance, with the document reference |
| Change notification | Exchange circular feed monitored; vendor contractually obliged to support within a stated lead time |
| Test window | Version change tested in the exchange's simulated environment before production |
| **Certification** | Protocol upgrade is a certification event, not a deployment; plan it against the [certification calendar](/broking-kyc/finix-broking-setup/setup/10-certification-mock-golive/) |
| Rollback | Where the exchange supports parallel versions, a rollback path; where it does not, the cutover is one-way and must be planned accordingly |
| Behaviour changes | A new version may change semantics, not just layout — for example the discontinuation of multileg orders with a market price condition. Read the change notes, do not diff the layout only |

## 7. Market data

| Aspect | Design |
|---|---|
| Source | Exchange multicast per exchange and segment |
| Separation | Capacity-planned separately from order flow; a volatility burst multiplies ticks without touching order rates |
| Consumers on the path | Risk price checks, band validation, client display |
| Consumers off the path | Valuation, surveillance, reporting, client history — served from the separate store built from end-of-day files |
| **Staleness detection** | Per instrument, not per connection; a stale feed is silent and poisons every downstream number at once |
| Gap handling | Counted, alerted, and recovered per the exchange's mechanism |
| Reference data | Band revisions and other control messages arrive on this path and must be applied, not merely logged |

Why the two-store split matters: a margin call six months ago has to be explicable using the price that was used at the time. A tick from a live multicast feed is not a durable, reproducible record. See [environments and configuration](/broking-kyc/finix-broking-setup/stack/environments-config-baseline/#4-exchange-set-parameters-and-their-refresh-contracts).

## 8. Monitoring

| Signal | Why | Alert on |
|---|---|---|
| Session state per instance | Basic availability | Any change |
| Heartbeat | Liveness | A single miss |
| **Sequence continuity** | Divergence detection | Any gap, immediately |
| Round-trip latency percentiles | Degradation precedes failure | 95th and 99th percentile movement |
| Message rates, in and out | Capacity and anomaly | Deviation from the expected profile, including **unexpected quiet** |
| Rejection rate and code distribution | Configuration and behaviour defects | Rate change or a new code appearing |
| Unacknowledged order age | Orders in limbo | Any order unacknowledged beyond a threshold |
| Market data staleness per instrument | The silent killer | Per-instrument threshold |
| Link utilisation | Headroom | Approaching the planned ceiling |
| Certificate and credential expiry | Scheduled outages | 60, 30 and 7 days |

The "unexpected quiet" row is worth emphasising. A connection carrying no orders at 09:30 is an incident even though every component reports healthy, and only a volume-profile alert catches it.

## 10. Exception paths

| Situation | Response |
|---|---|
| Primary link down, secondary healthy | Automatic failover; verify sequence continuity after failover, do not assume it |
| Both links down to one exchange | Stop new orders for that exchange and segment; preserve and display last-known order state; escalate |
| Sequence gap | Highest-priority connectivity incident: stop new flow in that segment and reconcile against the exchange |
| Session established but no market data | Block market orders and price-dependent risk decisions in scope |
| One BSE segment session down | Stop that segment only; the others continue; say so precisely in client messaging |
| MCX session drops after 20:00 | Evening escalation path; if a tender deadline is approaching, escalate to the clearing member and the exchange immediately |
| Exchange announces an unscheduled protocol change | Assess, test in the simulated environment, plan certification; do not deploy to production untested |
| Latency degradation without failure | Treat as an incident; degradation is the warning |
| Unexpected silence on a healthy connection | Investigate as an incident; verify with a test order where safe |

## Practical notes

- **Name the segment in every BSE runbook and alert.** Sessions are per segment, and ambiguous scoping produces ambiguous incident handling.
- **Monitor sequence numbers, not just connections.** It is the only signal that detects silent divergence.
- **Put protocol versions in the configuration register with an owner.** Exchange upgrades arrive by circular and the window is finite.
- **Read protocol change notes for semantic changes.** The discontinuation of market-price multileg orders is the kind of change a layout diff would miss entirely.
- **Alert on quiet.** An expected-volume profile is cheap to build and catches failures nothing else catches.
- **Contract vendor support to 23:30 for MCX.** A commodity session with day-shift vendor support is an unmanaged risk.
- **Treat the Trading Access Point, if used, as a first-class component.** It has a failure mode, a latency cost and a version.
