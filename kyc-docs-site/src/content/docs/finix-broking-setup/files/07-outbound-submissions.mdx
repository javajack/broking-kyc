> **Why this page is structured this way:** Inbound files fail loudly — something is missing and a gate blocks. Outbound submissions fail **quietly**, because the firm's own systems record a successful send regardless of what happened at the other end. That asymmetry is the whole subject of this page, so it is organised around proof rather than around transmission: what was sent, what came back, whether the counts agree, and who looked. Section 6 is the register that makes it auditable.

## TL;DR

- **An unread response file is an unmade submission.** This is the single most important sentence in the plane.
- **Reconcile counts, not statuses.** Accepted records against submitted records is the only check that detects the silent failures.
- **Several failures are invisible by design**: a wrong filename ignored rather than rejected, a zero-byte file rejected, an out-of-sequence batch rejected, a missing trailing newline halting processing partway.
- **Some submissions are web forms, not files** — a trade annulment and a market-maker declaration among them — so the register must accommodate a submission with no filename.
- **Construction rules matter as much as content rules**: record ordering within a file, batch-number semantics that differ by family, and headers that are required in one direction and inapplicable in the other.
- **Filing at one exchange now counts as filing at all** for a defined list — but that list has notable absences.

## 1. Why outbound is different

| Property | Consequence |
|---|---|
| The firm initiates | There is no expectation at the far end that something should have arrived, so **nothing is missing from anyone else's perspective** |
| The firm's systems record success | A send that was ignored looks identical to one that was processed |
| **The only evidence is the response** | Which means the response is part of the submission, not a confirmation of it |
| Deadlines are the firm's to meet | A rejected submission discovered after the deadline is a **late** submission, not a corrected one |
| Rejections are often **per record** | So a file can be substantially accepted and partially not, with no overall failure signal |

## 3. Submissions that are not files

The register must handle these, because a submission with no filename still has a deadline and still needs evidence.

| Submission | Form |
|---|---|
| **Trade annulment request** | A web form, with the counterparty's consent required within a defined window after the request or the close, whichever is later |
| Market-maker blackout declaration | A web form |
| **The cash and cash-equivalent report** | Electronic mail to a named clearing address |
| **The concert-party disclosure** | Electronic mail to a named address |
| Breach self-reporting by certain participant categories | Electronic mail to the same address |
| Penalty review request | A portal submission — **requests by electronic mail are explicitly not considered** |
| Alert disposition | A dashboard status update |
| Various applications | Portal workflows with attachments |

**For each, the register records the channel, the recipient, the evidence of submission, and what constitutes acknowledgement** — which for an electronic-mail submission may be nothing, in which case the sent record and the retained working papers are the evidence.

## 4. The silent failure modes

| Failure | Behaviour | Detection |
|---|---|---|
| **Wrong filename** | **Ignored**, not rejected; on the extranet renamed to mark it failed | The expected response never arrives |
| **Zero-byte file** | Rejected | No accepted records |
| **Out-of-sequence batch** | Rejected | No accepted records |
| **Missing trailing newline** | **Processing breaks partway** | Accepted count below submitted count |
| Per-record rejection | The file is accepted, records are not | **Count reconciliation** |
| Multiple errors in one record | **Only the lowest-numbered reason code is reported** | A corrected record can fail again immediately |
| Submission after the sign-off date | Rejected with an explicit message | **Treated as non-reporting** |
| A response file nobody reads | Nothing happens at all | **The response-file monitor** |

## 5. Construction rules

| Rule | Family |
|---|---|
| Downward records before upward records | Cash collateral allocation |
| Batch unique and sequential across segments for the day | Cash collateral allocation |
| Batch sequential from the first | Margin reporting |
| **Batch deliberately non-sequential** | Security release — **a gap is not a missing file** |
| All records, same batch number, every file | Voluntary auction |
| **No header** | Early pay-in allocation |
| Header always present in the response | Margin reporting |
| Specific member-code form | Position-limit reporting |
| One record per client code of the same participant | Related-investor information |
| Commas inside a filename | A code-modification response — **quote paths, do not split on commas** |
| Pre-populate from a data export | Collateral release — avoids reference mismatches |

## 6. The submission register

One row per submission type, and one record per instance.

| Field | Content |
|---|---|
| Submission identifier and business name | — |
| Recipient and channel | Portal, interface, extranet, electronic mail, web form, dashboard |
| Cadence and deadline rule | **The rule, not a fixed date**, where it is relative |
| Where filed | The designated exchange where single filing applies |
| Producing desk | Responsible for accuracy |
| **Accountable role** | Compliance officer for filing in most cases |
| Construction rules | From section 5 |
| **Expected response**, and by when | The absence of a response is itself a finding |
| **Count reconciliation performed** | Accepted against submitted |
| Rejections and their remediation | With the resubmission |
| Acknowledgement stored | Where one exists |
| Sign-off or correction window | Where applicable |
| Escalation on rejection or absence | **Immediate, not a daily digest** |

## 7. Single filing, and its absences

| Element | Position |
|---|---|
| The reform | For a defined list of common submissions, filing at **one** exchange counts as filing at all, where the member is registered at several |
| What stays local | **Processing, monitoring and supervision remain with each exchange** |
| The list's composition | A substantial block traces to designated-large-broker obligations; the remainder are general |
| **A notable absence** | **The authorised-person inspection report is not on the list** — only a declaration about authorised-person supervision is, and that is a designated-large-broker obligation. **The inference is per-exchange filing, consistent with per-exchange authorised-person approval. Confirm it** |
| The rule for the register | The list answers **where** to file, not **whether** something is owed |

## Practical notes

- **Monitor response files as a first-class operational stream**, with immediate alerting. It is the only control that catches the silent failures.
- **Reconcile counts every time.** A status field is not evidence.
- **Register the non-file submissions.** A form or an electronic mail with a deadline is a submission, and it will otherwise be tracked nowhere.
- **Store deadlines as rules.** Several are relative to annually published calendars.
- **Check what is not on the single-filing list.** The absence of the authorised-person inspection report is the known case; there may be others.
- **Treat a post-deadline resubmission as a late submission** in the record, because that is what it is, and say so to compliance at the time.
