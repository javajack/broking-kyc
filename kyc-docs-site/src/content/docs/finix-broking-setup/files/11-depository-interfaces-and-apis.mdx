> **Why this page is structured this way:** The file layer is already covered in [depository files](/broking-kyc/finix-broking-setup/files/06-depository-files/), so this page deals only with the transport and interaction layer above and beside it. It starts by separating three things that vendors and brochures routinely blur — a programmatic interface, a file channel and a portal — then lists what each depository publishes, then classifies operations as synchronous, asynchronous or file-based. The two authorisation flows that matter most to a broker, margin pledge and eDIS, come next because they involve the client and cannot be automated away. The cut-off section is last and carries the main analytical point: an API changes how an instruction travels, not when the depository will accept it. The gaps section is not an appendix; roughly half of what a build specification needs is not in any public document.

## TL;DR

- **<abbr title="Central Depository Services (India) Limited">CDSL</abbr> has expressly synchronous interfaces; <abbr title="National Securities Depository Limited">NSDL</abbr> is not a file-only depository.** CDSL's February 2026 migration notice labels early pay-in, margin pledge and normal pledge as synchronous and re-pledge as asynchronous. NSDL publishes early pay-in with a response, callback and enquiry, broker eDIS and margin-pledge integrations, and account APIs. `[public]`
- **A synchronous label does not mean the business outcome is complete.** The published material does not say whether a successful response means syntax accepted, instruction registered, consent received, pledge accepted, ledger posted or clearing-corporation credit recognised. Model those as separate states.
- **No generally available live holdings or client-master API is established at either depository.** What is published is reports, downloads, investor views and standardised files. Hold a reconciled local view with a source timestamp and label it stale when it is.
- **The public catalogue is not the specification.** NSDL reports a 56-API Digital Gateway, but its full inventory, versions and per-participant enablement were not recovered, and CDSL's per-service credentials, callbacks and limits are not published. Obtain the participant packs before promising anything.
- **UDiFF standardises the file, not the transport.** It does not define a common HTTP contract, credentials, token grammar or webhook protocol across depositories. Version the parser and the API contract separately.
- **Margin-pledge and eDIS authorisation run through depository-controlled client steps.** The client authenticates with the depository, using <abbr title="One-Time Password">OTP</abbr> and, at CDSL, a <abbr title="Transaction PIN">TPIN</abbr> generated and delivered by CDSL. The broker cannot execute the consent headlessly.
- **An API transport does not erase a business window.** A call that must still land inside a depository or clearing-corporation cut-off is not real-time in any sense a client cares about. Keep every clock separate and configurable.

## Conceptual overview

Three different things get called "the depository API". A **programmatic interface** is a request-response service reached over a network by the participant's own software, with its own credentials and a defined response. A **file channel** carries instructions or results as files, whether uploaded through a screen, an automation tool or an API endpoint that accepts a file. A **portal** is a human-facing screen, such as a client-entry site or a participant back-office application, that may produce files or accept them but is not a server-to-server contract. The classification matters because the three fail differently. An API fails with a response or a timeout. A file fails with a rejection report some time later. A portal fails with a person noticing. The published material shows that both depositories use all three, often for the same business operation.

The second point is that "file", "batch" and "end of day" are not synonyms. A file can be submitted through an API and processed intraday. An asynchronous API completes through inquiry, callback or report, and that is not necessarily overnight. Equally, the fact that an interface is file-based does not prove the underlying business operation is batch-only. The research behind this page is careful on exactly this: where no synchronous contract is established, the correct reading is "unresolved", not "only batch exists". That is particularly true of NSDL, whose reported 56-API Digital Gateway is only partly visible in public material.

The third point is the one that decides what a firm can promise a client. Even where an interface is explicitly synchronous, the response answers the question the interface was built to answer, and that is usually narrower than the question the client is asking. A pledge setup that returns synchronously has told the broker the request was handled; it has not told the broker that the client consented, that the pledgee accepted, or that the clearing corporation has recognised the collateral. The same applies to eDIS: authorisation can complete online while the debit and settlement remain separate events later. Every one of these is also bounded by clocks the API does not control — a depository weekday end of day, a clearing corporation's pay-in deadline, a one-time password's validity, a <abbr title="Depository Participant">DP</abbr> approval due the same day.

The fourth point is evidential. This page reflects what the depositories and their circulars publish. No authenticated production call was made in the research, so published URLs are published addresses and published labels are statements in official documents, not tested behaviour. Where the public material stops, this page says so and treats the item as something to obtain from the depository under the participant arrangement. For the file families themselves, and for the ingestion timing they feed, see [the ingestion cadence map](/broking-kyc/finix-broking-setup/files/10-ingestion-cadence-map/).

## 2. Three interface classes and what each means

| Class | What it is | Failure signature | Consequence for the build |
|---|---|---|---|
| **Programmatic interface** | Network request from participant software; response may be synchronous, or completion arrives later by callback, inquiry or report | Error response, timeout, or an accepted request that never completes | Persist the depository request identifier; on an ambiguous timeout, inquire before resubmitting |
| **File channel** | Instructions or results as files, uploaded by screen, automation tool or an upload API, and downloaded as reports | Rejection report after the fact; partial acceptance | Correlate file results to the originating instruction; see the rejection rule in [depository files](/broking-kyc/finix-broking-setup/files/06-depository-files/) |
| **Portal** | Human-facing client-entry or participant application | A person notices, or does not | Not a server-to-server contract; do not treat an online screen as an automation interface |

| Misreading | Why it is wrong | Consequence |
|---|---|---|
| "Asynchronous means overnight" | Asynchronous means completion follows separately; it is not necessarily end of day | Treating repledge as a batch job and polling once a day |
| "File-based means batch-only" | A file can be submitted through an API and processed intraday | Marking an operation unavailable intraday when the contract is simply unpublished |
| "No synchronous API published means only batch exists" | Absence from the public catalogue is not absence of the facility | Asserting non-existence where the correct state is unresolved |
| "A vendor holdings endpoint proves a depository holdings API" | A generally available synchronous depository holdings endpoint was not established | Promising live holdings the depository does not contractually supply |

## 9. eDIS and TPIN integration mechanics

| Layer | CDSL | NSDL | Consequence |
|---|---|---|---|
| Broker entry | Client signs in to the broker or DP portal or app; encrypted transaction data is handed to CDSL | Broker web or app initiates Demat Gateway authorisation | The broker hosts the entry, not the consent |
| Credential boundary | CDSL generates the TPIN, delivers it directly and does not give the DP access to view, edit or store it | SEBI requires depository-generated OTP and PIN or password for eDIS mandates; the exact NSDL provisioning specification is not published | The broker never holds the credential |
| Current factors | TPIN plus OTP | NSDL advertises OTP authentication; read with SEBI's PIN or password requirement, not as proof that a password factor is absent | NSDL terminology is not CDSL TPIN |
| Consent result | Success or rejection returned to the DP; CDSL stores validated transaction details | Callback to broker and update at participant system | Consent evidence is held at the depository |
| Actual debit | DP subsequently submits transactions; CDSL matches them to validated details | CM submits debit to the client's DP; NSDL validates against CC obligation data | Debit is a second event |
| Granularity | For on-market eDIS, ISIN and quantity with a single settlement number and date | Same regulatory description | One mandate does not cover a later settlement |
| Revocation | CDSL lists revocation of pre-trade consent | Order status check is listed; a public revocation endpoint is not published | Revocation coverage differs |

Keep separate consent, securities-instruction and execution records. Do not mark a delivery done on an OTP-success message alone. The money-side equivalent of this separation is described in [real-time limit updates](/broking-kyc/finix-broking-setup/money/09-realtime-limit-updates/).

## 10. UDiFF versus APIs

| Question | Position | Consequence |
|---|---|---|
| What is standardised? | SEBI guidance standardises information and file structures across trading, clearing and depository operations; the representation is CSV with ISO-derived field tags | A data schema |
| Does ISO tagging imply an ISO 20022 network API? | No such conclusion follows from field naming in CSV | Do not infer a message network |
| Does UDiFF define a common HTTP contract, credentials or webhooks? | No reviewed authority establishes one; the programme is file and data-format harmonisation, not API interchangeability | Transport, authorisation and state translation stay depository-specific |
| Can an API carry a UDiFF file? | CDSL publishes BO and Common Upload APIs as well as standardised BO and transaction upload files; the accepted schema version per API must be confirmed | Schema and transport are separate layers |
| What stays file-oriented? | Bulk account and transaction intake, and reconciliation, master, holding and transaction exports | Reconciliation remains a file job |
| Current versus proposed | CDSL's harmonisation page, updated 12 October 2026, lists v3.0.1.2 and separately labels v3.0.1.3 as a proposed format; NSDL's October package is named for v3.0.1.2 but contains both v3.0.1.2 and v3.0.1.3 workbooks | Archive inclusion is not an activation notice; an effective date for v3.0.1.3 is not stated |

Reuse schema interpretation, validation and reconciliation concepts across depositories where the publications support it, and keep transport, authorisation and state translation separate.

## 11. The limit of real time: API transport does not erase business windows

The times below are published operating times. No API-specific extension is inferred from any of them, and a publication date, a deadline and a tested operational fact are kept separate.

| Clock | Published timing | Scope and limit | Consequence |
|---|---|---|---|
| CDSL margin-pledge OTP | 15 minutes, regeneration allowed | OTP validity, not an API service-hours limit | A client can be inside the OTP window and outside everything else |
| CDSL manual pledge authentication | Through end of day of the execution date; uncompleted authorisation cancels | Exact wall-clock end of day for every date and module is not stated | A pledge raised late can lapse without any API error |
| CDSL LAS DP approval or rejection | Same day as request generation, per the 15 July 2026 circular | Exact intraday cut-off is not stated; API initiation does not remove DP processing | A lender-originated pledge waits on a person |
| NSDL SPEED-e current-date instructions | 19:00 on weekdays and 15:00 on Saturdays; future-date instructions can be entered later | The rule is specifically SPEED-e, not all broker APIs | Do not apply it to the Demat Gateway |
| NSDL system weekday end of day | Extended availability to 22:30, then end of day; excludes Saturdays, Sundays and holidays | System availability is not a promise that every settlement operation stays eligible until 22:30 | Availability and eligibility differ |
| NSDL Sunday account activity | Accounts opened up to 18:00 on a Sunday can activate the same Sunday; later openings activate after Monday beginning of day. Insta Demat, CMA and DAN APIs usable; ordinary market, off-market, pledge, demat and remat execution with a Sunday business date is excluded | Per `NSDL/POLICY/2026/0136`; Sunday UCC data arrives in five receipts and DP downloads follow in Monday's first batch `[not yet in index]` | A Sunday-opened account and its broker-visible UCC export have different availability times |
| NSDL G-Sec own-account transfer | 16:30 Monday to Friday; 13:00 on a working Saturday | A specialised transfer deadline, not a general broker window | Do not generalise |
| <abbr title="NSE Clearing Limited (formerly National Securities Clearing Corporation Limited)">NCL</abbr> securities early pay-in | General 21:00, and 20:00 for <abbr title="Unified Payments Interface">UPI</abbr> clients, subject to change and running-account-settlement days | A clearing-corporation deadline, not a depository API or pledge-OTP deadline; verify the daily schedule | The clearing corporation sets this clock |
| CDSL mutual-fund redemption pay-in | NCL and <abbr title="Indian Clearing Corporation Limited">ICCL</abbr> originally 19:15 from 1 June 2025; the ICCL deadline changed to 19:30 by a 2 September 2025 circular | Covers specified MF redemption settlement, not every equity debit; do not keep applying 19:15 to ICCL | A stale constant is a live defect |
| CDSL API migration dates | 27 February and 31 March 2026 | Migration deadlines, not daily instruction cut-offs | Do not confuse them |
| Generic API and file service hours; margin release; ICCL and <abbr title="Multi Commodity Exchange Clearing Corporation Limited">MCXCCL</abbr> collateral release | No complete service-by-service calendar, maintenance window or common cross-CC cut-off is published | Obtain the DP and CC schedules independently; do not import <abbr title="National Stock Exchange of India">NSE</abbr> securities early pay-in times into commodity collateral processing | Configure from the participant production operating pack |

The analytical conclusion follows directly. A synchronous early pay-in call placed after the clearing corporation's deadline is a fast rejection or a late instruction, not a timely one. A margin pledge accepted by the API but still awaiting the client's OTP, the pledgee's confirmation and the clearing corporation's recognition has not increased available margin. The correct promise to a client is therefore stated in terms of the last event that completed, not the first response that returned. The cadence at which depository outputs actually arrive is in [the ingestion cadence map](/broking-kyc/finix-broking-setup/files/10-ingestion-cadence-map/).

<Aside type="danger" title="Do not credit on the first response">
Never mark a pledge as collateral, a delivery as made or an account as active on a synchronous acknowledgement alone. The published material establishes that setup interfaces respond synchronously, not that consent, pledgee acceptance, ledger posting or clearing-corporation credit has occurred. Credit on the final evidence, and show the client the pending state until then.
</Aside>

## 13. Exception paths

| Situation | Response |
|---|---|
| Timeout on a pledge, early pay-in or upload submission | Inquire using the published inquiry or status route before any resubmission; persist the depository identifier |
| Synchronous success but no downstream confirmation | Leave the item in a pending state, show it to the client as pending, and chase through the inquiry or the pledgee |
| Callback received with no matching request, or duplicate callback | Hold for reconciliation; compare against inquiry and the participant record; never apply twice |
| Client OTP expired or authorisation lapsed at end of day | Re-initiate; at CDSL regenerate within the 15-minute window or raise a new request; do not assume the NSDL window |
| Instruction submitted after a cut-off | Treat as late; escalate to the DP and CC schedule; do not resubmit blindly |
| Sunday-opened NSDL account not visible in the UCC export | Expect the Monday first-batch download; do not treat as a failed seeding |
| Old CDSL hostname or delayed version still in use | Move to the current address; the shutdown dates have passed |
| Holdings from a download disagree with the local view | Mark the figure stale, reconcile from the latest full report, and do not overwrite silently |
| A needed interface is not in any public document | Record it as an open procurement item with the depository; do not guess an address, field or header |
| Public material conflicts (NSDL eligibility, CDSL count-API IV) | Request written clarification from the depository; do not implement by guesswork |

<Aside type="caution" title="What the published material does not establish">
Several things a build specification needs are simply not public. NSDL's full 56-API inventory and CDSL's complete entitlement and version inventory were not recovered. The meaning of each successful response, from syntax accepted to clearing-corporation credit, needs the actual response dictionaries. A contractual live holdings or client-master API with a freshness guarantee is not established. Margin and repledge-specific release and invocation, including chain unwinding and partial quantities, is not established, and normal-pledge addresses must not be generalised to it. Per-product signing, token lifetimes, quotas and timeouts, the margin-link token grammar, callback signature and retry rules, and NSDL's OTP lifetime are all unpublished. There is no single service-hours table for API and file paths, and NCL, ICCL and MCXCCL collateral windows are not consolidated. No authenticated production test was performed, so every statement here is what an official publication says, not what a call returned. Promise synchronous customer outcomes only after entitlement, test and response-finality checks; until then, design for explicit pending states, inquiry, reconciliation and manual exception handling.
</Aside>

## Practical notes

- **Request the participant packs first.** The public catalogue is a map, not the specification; versioned payloads, addresses, entitlements, test data, certification steps, service windows, limit tables and callback guarantees are a procurement item.
- **Do not label a response by its HTTP status.** Store what the response means in the depository's own terms, then map to an internal state only after the response dictionary is in hand.
- **Inquire before you resubmit.** A repeated financial instruction after an ambiguous timeout is the costliest error in this layer, and no idempotency rule is published to protect against it.
- **Keep every clock a separate key.** OTP lifetime, credential expiry, system end of day, settlement deadline and collateral-release window are different numbers set by different parties.
- **Never copy a CDSL value onto NSDL.** The OTP lifetime, the TPIN concept and the end-of-day behaviour are published for CDSL only, and the same applies in reverse.
- **Treat a callback as evidence needing validation.** A published callback does not establish a signed, retried, ordered webhook; compare it with the participant or clearing-corporation record.
- **Check entitlement before design.** A stock-exchange broker registration alone is not shown to confer access to every DP endpoint, and lender and trading-margin permissions should stay separate.
- **Version the parser and the API separately.** A proposed UDiFF format is not an effective one, and a file schema can change without the transport changing.
