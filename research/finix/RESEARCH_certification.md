## 1. Approval regime and the different layers of permission

| Question / software | Exchange requirement and operating consequence | Evidence |
|---|---|---|
| What does NNF mean? | NSE uses **Non-NEAT Frontend**; CTCL means **Computer to Computer Link**. “Neat-on-Net” is not the expansion used in the current NSE NNF circular. A terminal ID, exchange user ID, client code, order-routing tag and algorithm registration ID serve different purposes. | [verified] [NSE NNF master, definitions and §16][N1]; [NSE user-ID master, §5][N2]. |
| General approval gate | Broker software used in trading or real-time risk management must pass the applicable testing/auditor process and obtain the relevant exchange's approval before deployment. The SEBI baseline explicitly covers IBT, DMA, STWT, SOR and algorithmic trading. | [verified] [SEBI, 19 August 2013, software testing and deployment approval][S1]. |
| Exchange-supplied dealer terminal | NEAT/NEAT Plus, BOLT/BOLT Plus and MCX TWS have exchange-controlled distribution/access arrangements. Broker user-ID and location permissions still matter. NSE distinguishes exchange-terminal, NEAT-converted-to-NNF and NON-NEAT IDs; its Type-I system-audit treatment is different from broker-operated NNF. | [verified] [NSE user-ID master, §5][N2]; [NSE system-audit circular, applicability][N4]. [unknown] A separate broker software-certification filing for every unmodified exchange-supplied terminal release was not established across all three exchanges. |
| Dealer CTCL / custom front end / OMS / RMS | Prior NNF/CTCL product and member deployment registration is required. A dealer-terminal licence purchased from a vendor does not itself enable the member's exchange connection. | [verified] [NSE NNF master, §§1–3][N1]; [MCX CTCL categories][M1]. |
| Internet-based trading: web | IBT facility approval is required before offering client trading. NSE requires a member-specific application and audit evidence even for empanelled software. BSE expressly lists IBT approval as a portal activity. | [verified] [NSE NNF master, §§2,4][N1]; [BSE 20260313-24, original notice reproduced by TeamLease][B1]. |
| Mobile application / STWT / WT | Mobile order routing is an additional permission category, not automatically covered by owning a web application. NSE STWT eligibility builds on IBT permission; MCX similarly requires IBT approval and additional wireless permission. | [verified] [NSE NNF master, §5][N1]; [MCX wireless-trading requirements][M2]. |
| Algorithmic trading | Permission attaches to the algorithm and approved software/strategy, with an exchange identifier and approval for modifications. The retail framework also requires exchange empanelment of providers and broker due diligence; a provider's empanelment does not approve every deployment. | [verified] [SEBI retail-algo circular, §§5.I–III][S3]; [NSE NNF master, §§2,8][N1]. |
| Broker API access versus exchange protocol API | The exchange's API specifications describe how the member's software connects to its trading system. A broker API offered to clients is a separate regulated access channel, with its own facility, identification, authentication, RMS and retail-algo requirements. Calling it an “API” does not remove the software approval gate. | [verified] [NSE NNF master, §§2,8,16][N1]; [SEBI retail-algo circular][S3]. |
| Retail API: lower-rate client-generated algorithms | NSE's published threshold is **10 orders per second per exchange**, measured using the broker server's calendar-clock second. Its standards provide a route without individual client-algo registration below the threshold, but require algo tagging/generic identification, broker RMS and rate controls. This is not an exemption for the broker's API product. | [verified] [NSE NNF master, §§8.3.2.2–8.3.2.3][N1]. [uncertain] §8.3.2.2(3) also uses “require registration” while discussing generic IDs; obtain the current operational interpretation for generic-ID registration and the exact boundary before implementation. |
| Retail API security | The SEBI framework requires controlled API access, vendor/client-specific keys and static-IP whitelisting, OAuth-based authentication and 2FA; providers must be empanelled. NSE additionally requires daily API-session logout before the next trading day. | [verified] [SEBI retail-algo circular, §5.I][S3]; [NSE NNF master, §8.3.2][N1]. |
| DMA | Exchange permission for the broker's DMA facility/software is distinct from onboarding an eligible DMA client and reporting its mapped ID/UCC. DMA is not a generic label for any retail API. Additional algorithm approval applies where the DMA flow uses algorithms. | [verified] [NSE NNF master, §6][N1]; [NSE user-ID master, §5.2(b)][N2]. |
| Smart order routing | SOR requires exchange permission and routing/risk-control compliance. NSE's consolidated process specifies a **physical application** for SOR with the relevant supporting documents; do not assume its ordinary online NNF workflow covers every SOR step. | [verified] [NSE NNF master, §§2.2,7][N1]. [unknown] A current MCX SOR application route was not verified; do not transfer the NSE/BSE securities SOR process to commodities automatically. |
| Empanelled vendor product | Verify vendor empanelment, product registration, segment, facility and version. The broker then registers its own implementation and certifies testing and controls. Generic vendor marketing claims or another member's approval are insufficient evidence for this member's deployment. | [verified] [NSE NNF master, §§2.2.2,12][N1]; [MCX vendor-empanelment page][M3]. |
| In-house / custom / non-empanelled developer | NSE treats development through a non-empanelled vendor as the in-house route. It requires product/RMS descriptions and member-specific audit/testing. MCX publishes an in-house registration route, including exchange/vendor API development and software demonstration. | [verified] [NSE NNF master, §2.2.4][N1]; [MCX categories][M1]; [MCX technology FAQ, in-house and modification processes][M4]. |
| ASP-hosted product | ASP empanelment and the member's enrolment are separate layers. NSE's ASP member route has an enrolment form, agreement, undertaking and user-ID application; it is not identical to the broker-hosted vendor route. Auditor/ASP responsibilities must be checked against the applicable architecture. | [verified] [NSE NNF master, §2.2.1 and §13][N1]; [revised ASP/member formats effective 18 May 2026][N3]. |
| What the broker still certifies | Its actual product/version, segment and facility; member UAT; exchange-test and mock/simulation participation; order handling; pre-trade RMS; access/network/security controls; configuration and deployment. The broker remains responsible for orders and its service even when software is bought or hosted. | [verified] [NSE revised Annexure III and Additional Declaration][N3]; [SEBI software-testing undertaking][S1]. |
| Approval versus intimation | New facilities, new products and substantive changes use approval/registration routes. Terminal additions/changes use prescribed reporting/activation workflows; mock evidence and incident reports are reporting obligations. Neither “intimation sent” nor “vendor certified” proves software approval. | [verified] [NSE NNF master, §2][N1]; [NSE user-ID master, §5][N2]; [SEBI technical-glitch framework][S6]. |

### 2.2 Audit, security and hosting

| Control / submission | What must be demonstrated or distinguished | Evidence |
|---|---|---|
| Pre-approval system audit | This assesses the proposed trading system and its tests. It is different from the recurring system audit of the broker and the CSCRF cyber audit/VAPT cycle. Passing one does not establish completion of all three. | [verified] [NSE Annexures II/III][N3]; [NSE system-audit circular][N4]; [NSE cyber-audit circular][N5]. |
| Recurring NSE system audit | For the trading-member-only category, NEAT/NNF members with **at most 10 locations and at most 50 terminals** have Type-II audit once in **two years**; exceeding either threshold makes it **annual**. Algo users have Type-III **half-yearly** audit irrespective of size. Members also acting as DPs/offering other financial services have different minimum coverage; exchange/ASP software exclusions must be applied precisely. | [verified] [NSE/INSP/73850, Annexure A][N4]. These periodic classifications do not remove pre-approval requirements. |
| NSE auditor empanelment and visit evidence | Periodic system-audit reports must be certified by an exchange-empanelled auditor from the half-year ending **30 September 2025** onward. The April 2026 instructions require audit-plan/location details, geolocation and visit/team capture through **NSE Member Portal**, and retention of audit-team/working-paper evidence for **at least three years** by the respective responsible parties. | [verified] [NSE/INSP/73850, pp.1–2][N4]. This exchange auditor app is not the broker's client trading app. |
| Auditor certificate particulars | The member certificate records member identity/code, new/modification request, product, segment, version, vendor, strategy details where relevant, application type and dates of UAT, exchange-test and mock/simulation. It certifies the relevant OMS, systems/network, access, cybersecurity and pre-trade controls. | [verified] [NSE revised Annexure III][N3]. |
| System-auditor competence and independence | NSE's NNF auditor-selection norms specify recognised qualifications including CISA, DISA, CISM or CISSP and independence/conflict checks. Use the norms for the particular engagement rather than assuming an ordinary financial-audit qualification alone suffices. | [verified] [NSE Auditor Selection Norms attachment][N3]. |
| Cyber auditor | NSE's April 2026 cyber-audit norms require a **CERT-In-empanelled auditing organisation**, with independence requirements and relevant resources/experience. This is a different criterion from an individual holding CISA. | [verified] [NSE/INSP/73849, Annexure A][N5]. |
| In-house and customised software application security | CSCRF audit ToR checks **DAST, SAST, functional audit and VAPT after every major release** for critical in-house/customised software, with compliance through CERT-In-empanelled IS auditing organisations. | [verified] [NSE/INSP/73849, ToR 23(a), 23(a)(i), pp.64–65][N5]. |
| VAPT scope | Scope encompasses infrastructure, web/mobile applications, APIs and relevant cloud deployments. An infrastructure-only scan does not establish mobile-app/API penetration testing. Reports should identify the tested asset/build and exclusions. | [verified] [CSCRF VAPT scope and report format, NSE reproduction][N6]; [NSE inspection observations on omitted APIs/mobile/web scope][N10]. |
| VAPT filing versus detailed vulnerabilities | The prescribed submission includes report summary/declarations and remediation/revalidation material. The 2025 clarification says explicit vulnerability detail should not be submitted unless SEBI/exchanges ask; retain the detailed report. | [verified] [NSE/INSP/70471, CSCRF-aligned VAPT submission][N7]. [unknown] A single universal pre-approval VAPT upload field or report-validity age across NSE/BSE/MCX was not verified. |
| COTS vendor STQC: 2026 change | **NSE/INVG/76131, 2 September 2026**, requires prospective/existing empanelled vendors to obtain STQC application-security and functional certification under the CSCRF process. Scope includes CTCL, IBT, STWT, API and back-office products. This is a vendor-product requirement alongside broker deployment duties. | [verified] [NSE STQC circular][N8]. |
| STQC dates and provisional route | Existing registered latest versions: certificate due **28 February 2027**. Annual submission for period ending 31 March is due 30 June, starting with **31 March 2028**. New products/versions require STQC. Prospective-vendor provisional empanelment specifies lab acknowledgement of **completion of testing**; the existing-vendor new-product route specifies lab acknowledgement plus applicable documents. Final empanelment/product registration follows the certificate. | [verified] [NSE/INVG/76131, existing/prospective vendor provisions][N8]. |
| STQC changes / residual findings | Major-change triggers include core OMS/RMS, authentication/security, exchange formats, technology and segment changes. Delta testing must cover impacted dependencies. Pending STQC observations require the prescribed CTO-signed compensatory-control documentation where the provisional process permits it. | [verified] [NSE/INVG/76131 and annexures][N8]. |
| BSE/MCX STQC status | A BSE notice dated **3 September 2026**, **20260903-15**, is reproduced as adopting vendor STQC requirements. | [uncertain] [NoticeBlue reproduction][B3]; original BSE attachment could not be authenticated directly. [unknown] Corresponding MCX STQC implementation details were not verified. |
| Indian hosting | NSE's additional auditor declaration requires the **order-routing server in India**. MCX's wireless rules incorporate IBT requirements. This is not evidence of a blanket ban on every foreign CDN, analytics tool or app-store service. | [verified] [NSE Additional Declaration from auditor, IBT/STWT][N3]; [MCX wireless requirements][M2]. [unknown] Complete permitted cloud/data-residency architecture for each component needs a separate CSCRF/cloud-framework assessment. |
| Availability and fallback | NSE declaration covers redundancy/no single point of failure, onsite/offsite backup, confidentiality/integrity, access control and alternative order placement during internet failure. | [verified] [NSE Additional Declaration from auditor][N3]. |
| Two-factor login | NSE's **19 June 2025** advisory requires 2FA for each web/mobile login and termination of active sessions at day-end or the defined time to prevent sessions persisting across days. An already authenticated multi-day session is not a substitute for the required next login. | [verified] [NSE/COMP/68635][N11]. |
| Other authentication controls | The NNF auditor declaration checks initial password change, password policy, inactivity logout, valid-user access, transaction logs, encryption and firewall controls. Do not invent a universal idle timeout or password-expiry interval from wording that does not supply one. | [verified] [NSE Additional Declaration from auditor][N3]. [unknown] A universal fixed timeout applicable to all three exchanges was not established. |
| App-store publication | SEBI launched the **Google Play “Verified” label on 25 March 2026** for stock-trading apps associated with SEBI-registered entities. It identifies the regulated entity association; the release is not a replacement for exchange software approval. | [verified] [SEBI PR 20/2026][S7]. [unknown] Apple equivalent, store review SLA, compulsory publisher-account name and universal “publish before/after exchange approval” sequence were not established. |
| Authentic app listing | SEBI's investor-support page links exchange lists of recognised/authorised trading mobile apps, including NSE, BSE and MCX. A broker should reconcile the intended production app with the applicable exchange listing process. | [verified] [SEBI investor-support directory][S8]; [NSE app list][N12]; [BSE app list][B4]; [MCX app list][M6]. [unknown] Exact current package-ID/store-URL submission forms and update deadlines. |

## 3. CTCL / NNF terminals, user IDs and locations

| Topic | NSE operating rule / cross-exchange distinction | Evidence |
|---|---|---|
| Exchange user IDs | Apply through ENIT for the relevant exchange user-ID type, conversion and facility enablement after software registration. | Channel markers | NSE prescribes **111111111111 = IBT; 222222222222 = DMA; 333333333333 = STWT; 444444444444 = Client Direct API**. These identify the enabled exchange-user channel; the IBT entry is not every customer's app login. | [verified] [NSE user-ID master, §5.1(b)][N2]. |

| Register before use | Report activations **before routing any order**, and report activation/deactivation before enabling/disabling the server-side ID. | Broker's terminal register | Maintain the mapping of 12-digit ID to dealer login. | Location restrictions | Dealer terminals belong at the member's main/branch offices or registered authorised-person offices, and are operated by approved persons. | Modifications and relocation | NSE provides CTCL-ID Modification; permitted modifications become effective the next day. ### 3.1 Verified NSE penalties — do not transplant to BSE/MCX

| Contravention | Prescribed action in the reviewed 2026 NSE annexure | Evidence |
|---|---|---|
| Effective-date treatment | The standardised framework applies immediately to pending/newly determined cases after **17 April 2026** where penalties are reduced; otherwise to violations after that date, and to submission obligations whose due dates fall after it. Read the applicable transition and escalation rules before calculating a historical penalty. | [verified] [NSE inspection master, §10.1(3)][N13]. |
| Unauthorised extension / non-upload of CTCL trading terminals / unreported prohibited location | **₹1 lakh per location** at first instance; second instance **50% escalation**, third onwards **100% escalation**. The annexure also permits considering membership suspension in specified aggravated cases involving more than five unreported terminals and unregistered intermediaries/illegal trading. | [verified] [NSE inspection master, Annexure 1.1, item 115][N13]. |
| Delayed reporting of trading from an inactive/unreported terminal | **₹1,000 per terminal per trading day until reporting**, capped at **₹1 lakh per terminal**. This is a separately described contravention; do not automatically add it to every location fine without the exchange's finding. | [verified] [NSE inspection master, Annexure 1.1, item 189][N13]. |
| Reported details differ from member trading-system records | **₹5,000 per instance**, cap **₹1 lakh**; non-trading IDs excluded for this fine. Second instance **50%**, third onwards **100%** escalation. | [verified] [NSE inspection master, Annexure 1.1, item 117][N13]. |
